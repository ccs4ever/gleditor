`/tmp/xuzz-j14`. The script's `--chord`, `--type`, `--key`, and `--click` options stood in for user
input. Store paths, `xudu-dump`, and source inspection were diagnostic evidence, not substitute
journey actions. The complete logs, frames, and stores remain in `/tmp/xuzz-j14`.

The first run produced a four-cell `d.1` rank with `specimen`, `12`, `3.5`, and `true`. Its saved
operations contain a plain `SetValue`, an `int64` value of 12, a `double` value of 3.5, and a `bool`
value of true, respectively. These four kinds passed the write and on-disk type check. The
accessibility labels use `[text]` for every one, because that is the cell's role; they do not expose
the `ValueKind`. There is no user-facing kind inspector in this flow. The rank lacks an OpHandle and
ExternRef, so the six-kind step fails.

`Ctrl+H` displayed the hypertime map and its operation nodes (`map.png`). The map has no annotation
form, handle-creation action, or command to place a selected operation on the `d.1` rank. The
attempted pointer selection did not report an overlay hit (`map-selected.log`); this run therefore
does not establish that map-node selection works. The automatic `d.editions` metadata generated an
`op_handle` cell during save, but that cell targets operation 10 and is unrelated to any selected
operation or user annotation. It does not pass this step. The map currently builds from
`session_.store(0)`, so a newly created slice in another store is not its source. A fix belongs in
the map's store binding and Xuzz's map actions: bind the focused slice, expose the selected
`MicroversionId`, add an annotation form, then insert the returned handle on the focused rank.

The second slice was created through `Ctrl+Alt+N` and edited to `foreign-target`. `Ctrl+O`'s custom
path field loaded it alongside the first slice (`both-loaded.log`). No visible command or control
then selected a foreign `MakeCell` operation, registered the foreign scroll, or created an
`ExternRef` placeholder in the first slice. `Store::makeExternRef` exists, but an API call would
bypass the journey. A fix belongs in Xuzz's cross-store cell selection and insertion flow, with
scroll registration and persistent target identity handled by the store layer.

Both stores' `ops.nodes` contain their edits, yet reopening either showed `New Cell` rather than the
saved edit (`map-selected.log` and `both-loaded.log`). The reopened first slice also showed only its
initial cells, although the later rank operations are in the spool. The designated current version
stayed at the slice's genesis head while ordinary ZigZag actions advanced the slice head. The
transclude-to-cell path explicitly calls `setCurrentVersions({sliceHead()})`, but ordinary cell edit
and insertion paths do not. A fix should persist the new slice head after every successful ZigZag
mutation and verify reopening the same rank and typed values.

The annotation target, handle dereference, ExternRef resolution, later foreign-cell edit, and stable
foreign target could not be validated because the interface cannot create the two required cells.
The reopen failure independently blocks the final step.
