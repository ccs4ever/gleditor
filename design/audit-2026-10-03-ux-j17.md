## Findings

### 1. Links forged on a Ctrl+N page are invisible

The second link was forged with a Ctrl+N page active. It is in that page's store (its `make cell`
and `setLink` chain names both bench passages), but Alt+Shift+N never reaches it: "step link
refused: no links on screen", and the beams count one strand. `Session::addLink`
(`apps/xudu/session.cpp`) writes a link into the active document's store, and every Ctrl+N page is a
store of its own; `LinkBeams::rebuildStrands()` (`apps/xudu/beams.cpp` ~166, ~220, ~260) and the
beam picking at ~2075 read links only from `session.store()`, store 0. The first link worked only
because the default document was active when it was forged. It is the same store-0 assumption the
link resolver had (`ee5382a`), one layer up.

Fix: place strands and offer candidates from every open store, keying each candidate with its own
store's authority.

## Not defects

- **Superscript and subscript "do not render".** Runner (b) read its frames as unchanged; its own
  crop `b/s1_zoom_formats.png` shows "kbsuper" raised and "kbsub" lowered, and the lead's rerun
  (`lead/ss.png`) shows the same. They shift the baseline without reducing the size, which is a
  typographic choice rather than a failure.
- **The default document's tab reads "223,22".** A typo in the runner's script,
  `--capture …s1_transrc_formatted.ppm--select 223,223`, made `--select` part of a file name and
  `223,223` a positional argument, which xuzz opened as a document of that name. The same typo
  voided that run's split, so step 5's format-across-a-split was rerun by the lead.
- **The pouch card's + did nothing in the long session.** The isolated run passes; in the long one
  the click's pixel, calibrated with two documents open, hit something else once four were.

## Not confirmed

- Runner (a) saw a click on nothing followed by offset steps acting on the default document, leaving
  two stray page breaks there. Whether a click on empty space moves the caret to document 0 was not
  isolated.
- Right after one multi-paragraph `--type`, `--dump-a11y` reported `[caret 38]` with the caret
  visibly at 116; correct after any explicit placement. Not reproduced by the lead.

## After the run

Finding 1 is fixed in `10e7169`. Strands are placed from every open store, each naming its link by
store and id together, and Alt+Shift+N steps through the links of every store with a document open.
Not every open store, because the system xanadocs' format links are nothing the reader is looking
at. The lead reran step 4 (`lead/step4/`): one link forged with the default document active, one
with a Ctrl+N page active; Alt+Shift+N reaches each in turn and the panel reads both endsets.
`LinkInPageStoreTest` replays the case through the binary.

The same change filled the list `LinkBeams::describe` builds its link nodes from, which nothing had
ever filled. The accessibility tree now has "links between the open documents", one node per link,
its members and occurrences while it is selected, and their Click actions.

Both unconfirmed observations reproduced and were the harness's, fixed in `1f9b420`:

- **The caret offset.** The tree names a text run and a character in it, as the platforms expect;
  `--dump-a11y` printed the character alone, so the end of a three-paragraph document read as the
  last line's length (38 rather than 116). The dump now counts the runs before it.
- **Edits landing in the default document.** A click on nothing clears the caret, deliberately
  ("back to navigating"). A `--select` after that fell back to document 0 silently, which is how
  runner (a)'s missed click left two page breaks there. It now says so on standard error whenever
  more than one document is open.

All four suites pass (gleditor 539, xudu 1204, xuzz 56, zigzag 120).
