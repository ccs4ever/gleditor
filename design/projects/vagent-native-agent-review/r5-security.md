## BLOCKING

### 1. (§8.3, §13.4) 64-bit ioctl argument sign/high-bit extension bypasses TIOCSTI filter

**Problem:** On 64-bit Linux architectures (x86-64, aarch64), the kernel system call ABI prototype
is `asmlinkage long sys_ioctl(unsigned int fd, unsigned int cmd, unsigned long arg)`. The `cmd`
parameter is an `unsigned int` (32 bits), but in seccomp-bpf (`seccomp_data`), the
architecture-neutral argument array `args[1]` is a 64-bit register value (`__u64`). A standard
equality rule `SCMP_CMP_EQ` generated by libseccomp evaluates a 64-bit comparison:
`args[1] == TIOCSTI` (where `TIOCSTI = 0x5412`). If the caller passes `cmd` with high bits set (e.g.
`(1ULL << 32) | TIOCSTI`, or if glibc's `int ioctl(int fd, unsigned long request, ...)` prototype
sign-extends a signed integer), the 64-bit comparison fails to match the `EPERM` rule. The call
falls through to the allowlist rule for `ioctl`, reaching `sys_ioctl`, which casts `cmd` to
`(unsigned int)`, truncating the upper 32 bits and executing `TIOCSTI` (`0x5412`). An untrusted or
compromised native host can thus bypass the `TIOCSTI` filter to inject synthetic keystrokes into the
pty slave input queue, violating terminal isolation.

**Evidence:** `design/vagent-native-agent.md:540` admits "`ioctl` other than the refused requests
below;" and `design/vagent-native-agent.md:558-559` specifies
`- **EPERM, so a probe can observe the refusal.** ... ioctl with TIOCSTI, TIOCLINUX or TIOCSETD.`
without specifying argument bitmasking or `SCMP_CMP_MASKED_EQ`. In
`design/vagent-native-agent.md:1154`, the test probe executes `ioctl(grant, TIOCSTI, "x")`, which
passes `0x5412` with upper 32 bits zero, masking the bypass during testing.

**Fix:** Specify that libseccomp rules for `ioctl` command arguments on 64-bit architectures MUST
use `SCMP_CMP_MASKED_EQ(1, 0xFFFFFFFFULL, TIOCSTI)` (and similarly for `TIOCLINUX` and `TIOCSETD`)
to mask the upper 32 bits of `args[1]` before comparison. Even better, invert the rule: default
`ioctl` to `EPERM` and strictly allowlist only the specific terminal query and configuration ioctls
needed by ncurses (`TIOCGWINSZ`, `TCGETS`, `TCSETS`, `TCSETSW`, `TCSETSF`), comparing each with
`SCMP_CMP_MASKED_EQ`. Add an escape probe in §13.4 executing
`syscall(SYS_ioctl, grant, (1ULL << 32) | TIOCSTI, "x")` to assert that high-bit register variants
are blocked.

### 2. (§10.4) strict terminal filter permits DSR/CPR/XTWINOPS escape sequences

**Problem:** §10.4 specifies that the terminal relay between the pty master and the owner's terminal
emulator is a security boundary, defaulting to `vagent.native.terminal_filter = strict`. While
`strict` drops OSC, DCS, APC, PM, and SOS strings, it explicitly permits "CSI sequences for cursor
movement, erasure, attributes and private modes". CSI sequences encompass dangerous query and
control sequences supported by standard terminal emulators (xterm, GNOME Terminal, Alacritty, Kitty,
iTerm2):

1. Primary and secondary Device Attributes (`CSI c`, `CSI 0 c`, `CSI > c`).
1. Device Status Report and Cursor Position Report (`CSI 5 n`, `CSI 6 n`).
1. Window manipulation / XTWINOPS (`CSI Ps ; Ps ; Ps t`), including window title and icon queries
   (`CSI 20 t`, `CSI 21 t`) and window resizing/movement (`CSI 8 ; h ; w t`, `CSI 2 t`,
   `CSI 9 ; 1 t`, `CSI 3 ; x ; y t`).

When a terminal emulator receives `CSI 6 n` (CPR), `CSI c` (DA), or `CSI 21 t` (window title
report), it automatically formats a response sequence and transmits it into its standard input queue
(e.g. `CSI <row> ; <col> R`). In `vagent run`, this synthetic input is relayed directly to the
owner's interactive shell or input reader, allowing a compromised native agent to inject arbitrary
characters and commands into the owner's interactive session. Furthermore, unconstrained "private
modes" allow enabling focus reporting (`CSI ? 1004 h`) and mouse event reporting (`CSI ? 1000 h`),
flooding the input queue with synthetic data.

**Evidence:** `design/vagent-native-agent.md:718-724` defines the `strict` filter as passing "CSI
sequences for cursor movement, erasure, attributes and private modes" without a closed allowlist of
CSI final bytes or private mode parameters. Open question NQ6
(`design/vagent-native-agent.md:1342-1343`) acknowledges this list is only a starting point, leaving
the security invariant unenforced in v0.5.

**Fix:** Replace the open-ended definition of `strict` in §10.4 with an explicit, closed allowlist
parser. Permitted CSI sequences must be restricted strictly to display rendering: cursor positioning
(`A`, `B`, `C`, `D`, `E`, `F`, `G`, `H`), erasure (`J`, `K`), display attributes (`m` / SGR), and
exactly two vetted DEC private modes: `?25h`/`l` (DECTCEM cursor show/hide) and `?1049h`/`l`
(alternate screen buffer). All terminal status queries (`n`), device attribute requests (`c`),
window operations (`t`), ANSI key remapping (`p`), focus reporting (`?1004`), and mouse tracking
modes (`?1000`, `?1002`, `?1006`) must be dropped by the filter. Add an escape probe in §13.4
validating that synthetic queries (`CSI 6 n`, `CSI 21 t`, `CSI c`) emitted by the host produce zero
response bytes on the owner's terminal input.

## MAJOR

### 1. (§8.1, §8.3) Lifetime mprotect(PROT_EXEC) allowance enables JIT shellcode injection

**Problem:** §8.1 step 6 applies Landlock and seccomp *before* step 7 (`dlopen` of `module.so` and
declared FFI libraries). Because the dynamic linker needs to map executable ELF segments during step
7, `mprotect(..., PROT_EXEC)` is unconditionally permitted in the runtime seccomp allowlist (§8.3
line 535). Consequently, `mprotect` with `PROT_EXEC` remains available to untrusted native code and
foreign libraries during step 8 ("Serve") for the entire remaining lifetime of the host process. Any
memory corruption in the native module, libffi argument packing, or linked C libraries can be
exploited to allocate writable memory (`mmap` or heap) and transition it to executable via
`mprotect(PROT_EXEC)`, bypassing W^X protections and executing arbitrary shellcode.

**Evidence:** `design/vagent-native-agent.md:488-495` places `dlopen` in step 7 after seccomp in
step 6. `design/vagent-native-agent.md:535` includes
`mprotect (including PROT_EXEC: the dynamic loader needs it)` and `mmap` in the unrestricted seccomp
allowlist.

**Fix:** Transition the host to a progressive two-phase seccomp architecture:

1. *Phase 1 (pre-load, step 6):* Install an initial seccomp filter and Landlock rules to restrict
   network, process execution, and file writes while permitting `mprotect(PROT_EXEC)` and `openat`
   for the dynamic linker. This safely bounds ELF constructors running during `dlopen` in step 7.
1. *Phase 2 (post-load lockdown, between step 7 and step 8):* Once step 7 finishes resolving
   declared symbols, install a second, additive seccomp filter that explicitly returns `EPERM` for
   any `mprotect` call with `(prot & PROT_EXEC) != 0`, and restricts `mmap` to non-executable
   mappings (`prot & PROT_EXEC == 0`).
1. In addition, invoke `prctl(PR_SET_MDWE, PR_MDWE_REFUSE_EXEC_GAIN, 0, 0, 0)` in post-load
   lockdown. Since Linux 6.7 is already required for Landlock ABI 4, `PR_SET_MDWE` (available since
   Linux 6.3) hardware-enforces memory-deny-write-execute protection across all threads.

### 2. (§11.2, §11.4) Unchecked handle aliasing allows UAF and Double-Free on consumed handles

**Problem:** §11.2 introduces the `consumed` modifier for handle parameters, removing the handle
from the handle table upon function success (e.g. `delscreen(sp: Screen consumed)`,
`stdio.close(f: Stream consumed)`). However, §11.4 lacks static affine/linear verification and
runtime aliasing checks for `consumed` parameters:

1. A sequence call can pass the identical handle variable to multiple parameters of a function where
   one is `consumed` (e.g. `do stream_merge(s, s)` where the second parameter is `consumed`). libffi
   passes the same raw pointer to both parameters; the C library destroys the object via one
   parameter, while code in the library reading the other parameter accesses freed memory
   (Use-After-Free) or frees it twice (Double-Free).
1. A sequence can invoke multiple consecutive steps passing the same handle variable to `consumed`
   parameters (e.g. `do stdio.close(s); do stdio.close(s)` or
   `do stdio.close(s); let k := fgetc(s)`).
1. §11.2 and §11.4 fail to specify runner behavior when a handle token is missing from the table at
   runtime.

**Evidence:** `design/vagent-native-agent.md:810` defines `consumed (on a handle parameter)`.
`design/vagent-native-agent.md:829-830` notes
`A consumed handle is removed from the table only if the call succeeded.` §11.4 Rule 1 (`:888`)
states calls are type-checked against declarations, but defines no linearity constraints or alias
restrictions for `consumed` handles.

**Fix:** In §11.4 Rule 1, mandate that sequence validation at seal time enforces strict linear usage
for `consumed` parameters:

1. A handle variable passed to a `consumed` parameter cannot appear more than once in the argument
   list of that call.
1. A handle variable passed to a `consumed` parameter is marked moved/consumed and cannot be
   referenced in any subsequent `let` or `do` step.
1. In `finally` cleanup steps, a cleanup call taking a consumed handle is skipped if the handle was
   already consumed by an earlier step.
1. In §11.2, specify that if a handle token lookup fails in the handle table at runtime, the step
   immediately fails with cause `ffi_argument` (or `stale`), captures no pointer, and aborts before
   invoking libffi.

### 3. (§11.2, §11.4) Signedness and integer overflow in cstring_out(n) buffer sizing

**Problem:** §11.2 defines `cstring_out(n)` where `n` is another `c_int` parameter, sized as "a
runner-owned buffer of `n + 1` bytes", with the constraint that `n` is "at most
`vagent.native.max_out_bytes`". Because `c_int` is a signed 32-bit integer, checking only that
`n <= max_out_bytes` permits negative values of `n` (e.g. `n = -1` or `n = -100`). If `n = -1`,
`n + 1` evaluates to 0, causing the runner to allocate a 0-byte buffer. If `n < -1`, `n + 1` is
negative, which wraps around to a massive unsigned value when cast to `size_t` for memory
allocation. When the foreign C function is called with the allocated buffer and the negative `n`
parameter (e.g. `mvinnstr(y, x, buf, -1)`), libc functions treating `n` as unsigned `size_t` or
reading without lower bounds write beyond the allocated buffer, causing heap buffer overflow and
memory corruption in `vagent-native-host`. Furthermore, if `n = INT_MAX`, `n + 1` overflows signed
integer arithmetic, inducing undefined behavior.

**Evidence:** `design/vagent-native-agent.md:824` specifies `cstring_out(n)` as "a runner-owned
buffer of `n + 1` bytes" where "`n` is another `c_int` parameter, at most
`vagent.native.max_out_bytes`", omitting a non-negativity constraint.

**Fix:** Update §11.2 line 824 and §11.4 to explicitly require:
`0 <= n && n <= vagent.native.max_out_bytes`. The runner must validate this range before buffer
allocation; any value of `n < 0` or `n > max_out_bytes` must immediately fail the step with cause
`ffi_range`. Add an escape probe in §13.4 testing that `cstring_out` with `n = -1` and
`n = -2147483648` fails cleanly with `ffi_range`.

### 4. (§8.2, §13.4) Cross-platform sandbox parity gaps and missing platform escape probes

**Problem:** §8.2 summarizes future sandbox mechanisms for FreeBSD (Capsicum), OpenBSD
(unveil/pledge), macOS (Seatbelt), and Windows (AppContainer). However, the outlined mechanisms
suffer from critical security gaps:

1. OpenBSD: `pledge("stdio rpath prot_exec recvfd tty")` permits `TIOCSTI` via the `tty` promise and
   unconditionally grants executable page creation via `prot_exec`, violating W^X.
1. FreeBSD: Stating that libraries are "opened before `cap_enter` and loaded with `fdlopen`" implies
   ELF constructors run outside capability mode unless rtld capability mode loading is strictly
   ordered.
1. macOS: A Seatbelt profile restricting only `file-read*` and `network*` without
   `(deny mach-lookup)` leaves Mach and XPC IPC accessible, allowing child processes to escape
   isolation via system daemons (e.g. WindowServer, launchd).
1. §13.4 specifies escape probes exclusively for Linux syscalls (`open`, `socket`, `clone3`,
   `ptrace`, `TIOCSTI`, `memfd_create`, `int 0x80`), leaving non-Linux backends without defined
   security invariants or pass/fail acceptance criteria.

**Evidence:** `design/vagent-native-agent.md:501-506` lists platform mechanisms with known escape
vectors. `design/vagent-native-agent.md:1136-1162` defines probes solely for Linux on Landlock ABI
4+.

**Fix:** In §8.2, document the mandatory security invariants for non-Linux spikes:

1. On OpenBSD, mandate that `TIOCSTI` is disabled kernel-wide (`kern.tty.tk_can_tiocsti=0`) or
   blocked, and replace `prot_exec` with two-phase pledge (`pledge` without `prot_exec` after
   loading).
1. On FreeBSD, specify that `cap_enter` occurs before ELF constructors run, or pre-open library file
   descriptors and load via capability-aware `fdlopen` under `cap_rights_limit`.
1. On macOS, specify a Seatbelt profile with explicit `(deny default)` and `(deny mach-lookup)`.
1. In §13.4, specify an abstract matrix of mandatory security escape probes (filesystem write
   denial, network socket creation denial, execution/fork denial, terminal injection denial, W^X
   enforcement) that any non-Linux spike must implement and pass before backend acceptance.

## MINOR

1. (§8.3) **Unrestricted fcntl command set in seccomp allowlist:**
   `design/vagent-native-agent.md:532` admits `fcntl` on any descriptor without argument inspection.
   An adversary could invoke `fcntl(grant, F_SETOWN, ...)` or `F_SETSIG` to trigger asynchronous
   signals, or `F_NOTIFY` for dnotify. The filter should restrict `fcntl` commands to an allowlist:
   `F_GETFL`, `F_SETFL` (masked to `O_NONBLOCK`), `F_GETFD`, `F_SETFD` (masked to `FD_CLOEXEC`),
   `F_DUPFD`, and `F_DUPFD_CLOEXEC`.
1. (§8.3) **Explicit enumeration of openat2 in ENOSYS list:** Line 527 specifies that unlisted calls
   return `ENOSYS`, which correctly causes glibc 2.33+ `open()` to fall back to `openat`. However,
   `openat2` should be explicitly enumerated in the `ENOSYS` subsection beside `clone3`
   (`design/vagent-native-agent.md:548`) to ensure future implementers do not inadvertently map
   `openat2` to `EPERM` (which would break glibc fallback) or admit it to the allowlist without path
   controls.
1. (§8.1, §14.2 P20.7) **Atomic descriptor cleanup via close_range and
   POSIX_SPAWN_CLOEXEC_DEFAULT:** In §8.1 step 2 (`:482`), the host checks that fds 0–6 are open and
   closes any other. To guarantee no descriptors leaked from the control plane survive across
   `posix_spawn`, P20.7's spawn helper should set `POSIX_SPAWN_CLOEXEC_DEFAULT` in
   `posix_spawnattr_setflags`, and step 2 should invoke `close_range(7, ~0U, 0)` atomically before
   Landlock or seccomp initialization.
1. (§11.2) **Cryptographic handle token generation and type tagging in handle table:** §11.2 line
   825 represents declared handles to the agent as `{token: Str}`. To prevent handle forgery, token
   guessing, or cross-type handle confusion across sequence invocations, handle tokens must be
   128-bit CSPRNG-generated random hex strings, and the internal handle table must bind each entry
   to its declared `NativeHandleType` and host instance.
1. (§8.3) **Unrestricted mremap in seccomp allowlist:** Line 535 admits `mremap` without argument
   restrictions. After post-load lockdown, `mremap` should not be permitted to remap or expand
   executable pages, preventing relocation of mapped library code.
