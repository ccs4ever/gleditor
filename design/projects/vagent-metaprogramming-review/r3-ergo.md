## Findings

### R3-F1. MAJOR — §5.3 (item 1, lines 690-694): captured `let` locals are claimed "stable" — spec §5.8 puts locals on the *frame*, so they are the same ABI-debt case as parameters

**Problem.** "fragment emission and the merged emission resolve `cap$N` through `CompilerBindings` to **one cell: the captured binding's own cell** — for fields, module vars and `let` locals, whose cells are stable, that is true cell identity and reads stay live. … Frame parameters are the one ABI-debt case." But the document's own stated prerequisite is "the call/frame convention of §5.8" — and §5.8 says "the call's arguments **and locals** hang on that frame cell's `d.vars`/`d.values`" (vagent-agent-language.md:646-647). Under the frame ABI a `let` local's cell is per-activation, exactly like a parameter: orphaned at `Return`, read back as "the last-written value" by an escaped fragment. §5.3's "stable … reads stay live" is true only under the scalar kernel's `localCells_`-per-emission model (`compiler.cpp:853-855`), which is the no-call kernel — and which §5.8 supersedes for `def`/plan/handler bodies. The doc lists params as "the one ABI-debt case" while assigning locals to the stable class — under the owed ABI they are the *same* case. The two models also differ observably: static `localCells_` for a captured local is *shared across activations* (a recursive `def` clobbers it), whereas frame cells are per-activation — this is not free either way.

**Fix.** Move `let` locals into the stated ABI-debt case alongside frame parameters ("captured frame-bound bindings — parameters and `let` locals — read the binding's last-written value; the cell *is* the variable, at the price of dead frame cells until reclamation"), or rule that captured `let` locals mint static cells and price the cross-activation aliasing. Either way the observable rule must cover locals, not only params.

### R3-F2. MAJOR — §6.6 (lines 1188-1197), §6.1 layout (876), P16 item 1 (1212-1219): how a program-symbol call inside a fragment *binds* is unspecified — and under the int64 reading the "uniform rule" marks a cell `promote` then refuses

**Problem.** The r2-F1 fix records program-symbol references as name-records on `+d.refs` and has genesis "resolve them with `symbol_named`" — but the doc never says what the fragment's call graph contains. Two readings are each internally consistent and materially different:

- **(a) exec-time name dispatch** — the call op names the callee's qualified name (the name-record *is* the dispatch input); the `d.vars` name-walk runs per activation (the §5.7 walk `graft_method` already relies on, :1039). Then "they carry no cell identity" is literal, `closed`'s "no int-encoded program references" holds by construction, and genesis's "resolve name-records" is *validation* (fault/drop on unresolvable names, like patch names). Cost: an O(rank) name-walk per call — unpriced in §13; redefinition rebinding is uniform late binding.
- **(b) int64 + genesis rewrite** — the Call input holds `int64(defEntry)` at emission (Vortex `Call` executes `toInt(inputs[0])`, vortex_vm.cpp:854-857), name-recorded for rehydration. Then the ref cell is an emitter-minted int64 ref cell → the uniform rule of §6.6/P16-item-1 gives it the `d.mesh.relocation` marker → the pre-checkpoint re-kinds it `OpHandle` → `promote` requires `seen.contains(*target)` (`arena_manifold.cpp:1798-1809`) → the program-cell target is never promoted → **`promote` returns `nullopt` and every checkpoint carrying a learned `def`-calling fragment fails** — §9.3's flagship under literal application of the uniform rule. Under (b) the doc *must* state: name-record-targeted ref cells are exempt from the relocation marker; the name-record must identify the ref cell genesis rewrites (the stated shape `+d.values`→label, `+d.name`→qname points at no ref cell); and session calls keep the *old* binding while genesis rebinds — a session-vs-resume divergence worth a clause.

**Evidence.** "Calls by name (`navigate_to "G.travel"`, symbol dispatch) stay legal and durable; int-encoded program references do not" (:1191-1192) — asserts the outcome without specifying the mechanism; "P16 does **not** OpHandle-rewrite name-records" (:1193) implies an int64 exists to rewrite (reading b), while "they carry no cell identity" implies none does (reading a). The §6.6 genesis item (c) (:1227-1232) says "resolve name-records through `symbol_named`" without saying what the result is *for*.

**Fix.** One paragraph in §6.6 picking the model (recommend (a) — it matches the §5.7 name-walk the graft story already needs, makes `closed` structurally true, and needs no marking exemption), stating what the dispatch input is (a link to the name-record, or a `d.name` text input), pricing the per-activation walk in §13, and stating genesis's role (validation vs rewrite). If (b) is kept: exempt program-targeted ref cells from the uniform marking rule *in the rule's text* (a ref cell whose int64 names a non-fragment cell gets a name-record, never a `d.mesh.relocation` edge), point `+d.ref`→the ref cell for the rewrite, and note the rebind divergence.

### R3-F3. MAJOR — §6.3 (1044-1047), §7.2 (1298-1304): the graft signature check omits parameter *names* — but argument binding is by name, so a name-mismatched graft silently reads unbound frame slots

**Problem.** §7.2's descriptor comparison enumerates "parameter count and ordered type names, result type name, `pure`, `closed`" — no names. §6.3 says `graft_method` "must match the declared signature including effect-ness". Yet binding is by *name*: `run` binds frame slots by the fragment's parameter names (:980); spec §5.8 puts call arguments on the frame's `d.vars`/`d.values` name records (`#Bind`/`#Resolve` are name-keyed, vortex_vm.cpp:896-935); goal `planBindings` are checked by name against `parameterIndex_` (checker.cpp:1959-1972, name-keyed at :257-261); and `signaturesEquivalent` itself ignores names (:70-79). So `graft_method` installing `code"x: Int | x + 1"` onto `def f(a: Int)` passes arity+type, but every call to `f` writes frame slot `a` while the fragment body reads `x` — an unbound read the signature check waves through. Same for `graft_plan` ("the same parameter list the goal's other clauses share" must mean *names*, since selection binds the goal's arguments by name) and `graft_handler`.

**Fix.** Extend the descriptor comparison to ordered parameter *names* — the descriptor already carries them (§5.4: param cells are `+d.name`-labelled). Say so in §6.3 and §7.2: "signature match = ordered `(name, type)` pairs + arity + result + purity (+ effect-ness for `graft_method`)".

### R3-F4. MINOR — §6.6 (1177-1182): patch records "installed heads" — but `learn` installs `reify`d *copies* while registering the pristine *originals*

**Problem.** The patch's `+d.patch-head` chain records "one recorded head's `+d.name` label (installed heads in graft order …)". For `learn_*` the installed objects are reified copies labelled `reify:<src>:<serial>` — session-dead, unregistered; genesis resolves names through `code_named`, which finds only the *registered originals* (`src:`/`#label`). "Installed heads" must therefore mean the registered originals' labels — the wording says the opposite. Also unstated: a second `learn_*` of an already-registered head — register-idempotent or refused?

**Fix.** "each record holds the *registered* head's `+d.name` label — the pristine original, never the installed copy"; one clause on re-`learn` of a registered head.

### R3-F5. MINOR — §6.6 (1188-1203) / §5.3: the user-level `closed` contract is never stated — which captures are learnable and how learned calls bind

**Problem.** The mechanism is fully stated, but no sentence tells the user the contract: a `learn`able fragment is self-contained — literals, its own `CodeParams`, `believes`/`findall` reads, `cells"##…"`/`$` paths onto state-side cells, captures of *fields and module vars* — and program calls bound by name. Corollary never stated: **capturing a `let` local or a parameter makes a fragment un-`learn`able** (their cells aren't state-side — the `learn` refusal names them per §5.6 diagnostics, but the rule should precede the error). Nor is the rebind semantics stated: learned fragments resolve program symbols by name — under exec-dispatch they follow redefinitions uniformly; under the int64 model, session vs post-resume.

**Fix.** One paragraph in §6.6 (or the §5.3 tail): the self-containedness list, the locals/params exclusion, and the rebind rule.

### R3-F6. MINOR — §6.1 layout (862-879): descriptor `result` row and name-record shape are ambiguous

**Problem.** The `["result"]` row shows `+d.values→"Int" + result-type cell link` — the result-*cell* link's dimension is unstated (asymmetric with `produced`, which links the cell); `run` "finds the cells it spills" through it. And "name-records carry `+d.values`→label, `+d.name`→qualified name" — two name-ish edges whose roles (dispatch input vs genesis lookup vs closed-walk evidence) aren't distinguished.

**Fix.** Name the dims: e.g. `result`/`produced` each `+d.values`-point at their cells plus a `+d.name`-typed type cell; for name-records state which edge the dispatch reads and which the genesis/closed pass reads.

### R3-F7. MINOR — §6.7, §9.3, §6.1: labels containing `:` collide with qualified-name parsing; `graft_plan` goal-arg qualification unstated; `reify` serial scope across resume

**Problem.** `learn_plan("Feed", "patch:near_water", …)` makes a clause named `patch:near_water`; intentions and `plan_named` use `module:Agent.plan` — qualified, the learned name embeds a second `:` (`demo:Forager.patch:near_water`), and `reify:<src>:<serial>` does too. The split rule for these names is unstated. `graft_plan(goal: Str, …)` passes a bare `"Feed"` while `symbol_named` takes `(owner, name)` — is `goal` self-implicit or qualified? `reify`'s `<serial>`: a per-incarnation counter collides with promoted registered labels after `resume` — the loud-refusal consequence (or a durable seed) is unstated.

**Fix.** State the qualified-name parse (first-`:` split; names may not contain `:`/`."` rule, or rightmost-split), `goal`/`event` qualification convention, and the serial's scope.

### R3-F8. MINOR — §6.1 table / §6.2 / M3: `value_of` missing from the member table; `unlearn`'s param can't express method targets; `Code<T>` "carries" no arity; bare-`Code` wildcard needs an arity exemption

**Problem.** `value_of(c: Cell): any` is named in §6.2 prose (:995-997) but absent from the §6.1 surface table (purity unstated — presumably pure). `unlearn(clause: Cell)` can't express `learn_method` targets (a learned method is a symbol, not a clause — the r2 disposition said "clause-or-symbol"). §6.2 (:978) "when `c`'s type carries it statically" — `Code<T>` carries only `T`; the static check needs a statically-*known fragment* (M6's correct phrasing, :232) — unify. `run` on a bare-`Code` (wildcard) argument: result type unstated (`unknown`/`any`?). And M3 makes bare `Code` a wildcard while `Code→1` in the arity chain — `validateType` requires `arguments.size() == arity` (checker.cpp:565-566), so `Type{"Code",{}}` fails without a stated exemption.

**Fix.** Add the `value_of` row; `unlearn(clause_or_symbol: Cell)`; "statically known" phrasing in §6.2; `run(Code)` → `unknown`; arity rule "0 or 1 args for `Code`, wildcard when 0".

### R3-F9. MINOR — §8.3, §9.2, §9.3, §9.4, §5.5: examples break the doc's own rules

**Problem.** (a) §8.3, §9.2, §9.3 call `agent_cell`/`weight_of`/`set_weight`/`plan_named`/`learn_*`/`clauses_of` — all `std:meta`, which "is not implicitly imported" (§6.1) — no example shows `import std:meta`; as written they fail the allowlist (checker.cpp:2061-2067). (b) §9.3's `goal Feed` is undeclared in the excerpt — the `learn_plan` signature match the example teaches can't be verified (the r2 disposition's undeclared-decls item asked for a note); §9.4 `WithinBudget` same. (c) §5.5's `splice inc(static (2 * 3.14159))` — the only `inc` in the doc is §9.1's `n: Int` and `2 * 3.14159` is `Float` → arg-type error as written. ### R3-F10. MINOR — §5.1 EBNF: `'splice' Postfix` literally parses `splice c(3)` as splice-of-a-call-result — the peeling rule is only implied

**Problem.** `Postfix ::= Primary { '(' [ ArgList ] ')' | … }` — so under `'splice' Postfix` the operand of `splice c(3)` is the Call `c(3)`, and "splice of an expression value is always a check error" would fire — yet `splice c(3)` is the *intended* parameterized form (M3, §5.4, §9.1). The prose implies the operand's trailing arglist belongs to `splice`, never to a call — but the grammar doesn't say it. Also: the `splice`/`static` name rejection covers `def`/`method` only; a `let splice := 3` or parameter named `splice` parses fine yet is unreadable (prefix position is reserved) — dead-name bindings should get the same refusal.

**Fix.** `'splice' Postfix` plus the sentence: "when the operand's outermost Postfix ends in `( args )`, the arglist belongs to the splice; any other Call-shaped operand is a check error" — or restrict the operand to `Ident`. Extend the declaration refusal to `let`/`var`/param names `splice`/`static`.

### R3-F11. MINOR — §9.2 (1520-1523), §6.3: the `?`-export "refusal" is vacuous; `graft_handler` formals (`occurrence`/event fields) unstated

**Problem.** "a test whose `?`-binding the body needs is refused at the signature check" — no check can detect that: a body's `?` names are its own (a body can't even *write* a reference to the test's internal `?t`), so the situation is unparseable and the "refusal" never fires. And `graft_handler`'s "the clause's standard formals" never says what a handler's formals are — `occurrence` (or the `as`-name) and event fields are the binding a grafted guard/body needs; the convention (a param named `occurrence` typed by the event? the fields as formals?) is unstated — the r2-F9c residual.

**Fix.** Rephrase: "grafted tests never export `?`-bindings; a body cannot receive them". State the handler formals: `occurrence: <EventType>` bound by name (per the same name-binding rule as R3-F3).

### R3-F12. MINOR — M6/§6.2/§11: `run(c, [a,b])` vs `splice c(a,b)` — the spelling asymmetry has no user-facing justification

**Problem.** Users meet two arg-passing spellings: paren args for `splice`, a list literal for `run`. The doc cites the no-variadic surface (parser.cpp:316-339) once inside M6, but no refused-alternative line tells the reader why the parallel `run(c, a, b)` was rejected — the teachable rule ("one list packs the frame") is left implicit.

**Fix.** One row in §11 or one line in §6.2: "`run(c, a, b)` variadic spelling — refused: no variadic call surface; the list literal is the v1 spelling".

## Summary

v1.2 discharges all nine r2 findings in substance: `closed` is now defined over all outside references, `run` is a coherent checker special form, `cap$N` is a clean binding-table alias, labels/`reify`/templates/diagnostics/consume-contract all landed. The three majors are all in the *new* machinery's under-specification, not regressions: `let`-local captures are assigned to the "stable" class the §5.8 frame ABI contradicts (R3-F1); the program-symbol call binding inside fragments — the mechanism the whole r2-F1 fix rests on — is left as two incompatible readings, one of which marks a ref cell that then kills `promote` (R3-F2); and the graft signature check omits parameter names while binding is name-keyed, producing silent unbound reads (R3-F3). Nine minors: patch-record wording, the missing user-level `closed` contract, descriptor/name-record layout ambiguity, `:`-label parsing, `value_of`/`unlearn`/wildcard table gaps, example defects (missing `import std:meta`, undeclared decls, a Float-vs-Int arg, "today" honesty), the `splice` operand-peeling rule, the vacuous `?`-refusal + `occurrence` formals, and the run/splice spelling asymmetry.
