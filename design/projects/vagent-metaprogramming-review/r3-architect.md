## New findings

### 1. BLOCKING — the `d.validate` seen-set still holds exactly one mark; *neither* direction survives link eviction (§7.2 `:1316-1321`)

**Problem.** My r2 finding correctly diagnosed v1.1's direction as degenerate but prescribed a fix that fails identically — I should have caught this; the disposition ratified it ("N backlinks on the marker for free"), and v1.2 applied it. Both directions are wrong for the same reason: a dim gives each cell **one `+d` and one `-d` neighbour**, and `link` evicts *both* displaced ends. For `link(v2, d.validate, POS, marker)` where `marker -d.validate → v1` already holds: `existingLink(marker, dim)` yields `displacedIt = v1`, and `setOneSide(v1, dim, POS, noCell)` (`arena_manifold.cpp:1352-1373`, invariant stated `:1359-1361`) **clears v1's mark**. The membership test `linked(v, d.validate, POS) == marker` is then true only for the most recent mark — the "set" holds one cell, exactly the degeneracy r2 found in `marker +d → visited` (where the marker's single `+d` was the slot that evicted). The 1:1 edge constraint means *no per-cell set can live on a shared endpoint of one dim* — star membership is unrepresentable.

**Consequence.** `validate` walks op graphs that are never trees in practice: `emitStatement` binds shared literal cells (`cells_->zero`/`minusOne`/`unit`/`fail` minted once and bound into every `copy`, `compiler.cpp:530-532`, `:850-852`), and `Jump`-back `while`/`for` loops make real cycles. Without a working seen-set, a cyclic fragment's walk runs until `consumeWork` throws → `ActorDown` (`mesh_actor.cpp:473-479`) on **every** `graft` install, and even acyclic shared-cell DAGs get combinatorial re-walks.

**Fix.** Replace the shared-marker scheme with one that keeps endpoints unshared: `visited +d.validate → nonceCell` where `nonceCell` is a **freshly minted cell per mark** carrying the pass serial as content; membership is `t = linked(v, d.validate, POS); t && textOf(*t) == serial` — O(1), each nonce has exactly one `-d` neighbour so nothing evicts, staleness is killed by the serial. (Alternative: a `+d.validate` *chain* off the pass marker with O(n) membership by walk — no marker cells but honestly quadratic; or a depth-bounded walk replacing the set entirely.) Price the chosen scheme in §7.2's cost model — the current "O(n·membership)" hedge doesn't cover either.

### 2. MAJOR — the P16 checkpoint passes have no mutable-arena access path (§6.6 `:1220-1226`, P16 row `:1650`, §10.1 `:1628-1629`)

**Problem.** The re-scoped home is right — the adapter is the only component that owns emission and checkpoint timing — but the *access* is missing. The boundary hands out only `const ArenaManifold&`: `ActorCheckpointView::arena` is `const ArenaManifold &` (`mesh_actor.hpp:102-106`, filled from `actor->context->arena` at `mesh_actor.cpp:692-693`), `publishValue` takes `const ArenaManifold &` (`mesh_value.hpp:69-74`), and `MeshActorRuntime`'s public surface has **no mutable-arena accessor** (`mesh_actor.hpp:111-191`). The only mutable window into an actor's `WorkerContext` is the `Executor` callback during `pumpOne` (`executor_(..., *actor->context)`, `mesh_actor.cpp:472-480`) — and the vagent spec explicitly puts checkpoints *outside* that window: "The adapter checkpoints between `pumpOne` calls, never inside the executor" (`vagent-agent-language.md:379-384`). So "the adapter's pre-checkpoint pass … calls `setValueBits(OpHandle, …)` on the live arena" and "a post-publish pass writes `Int64` on the live arena" describe writes no API reaches. The genesis half is fine — rehydration can run inside the adapter-as-executor on the first post-`resume` turn, where `WorkerContext&` exists — so this is specifically the checkpoint-side pair.

**Fix.** Name the seam, either way: (a) the adapter-as-executor performs the ceremony inside its own callback — re-kind at end of the checkpoint-terminating turn (marks already zero), restore at next turn's start — which requires restating "the session graph never sees `OpHandle` kinds" as "never *executes* `OpHandle` kinds" (cells rest OpHandle between turns); or (b) `MeshActorRuntime` gains a mutable-borrow/hook (e.g. `withContext(pid, fn)` — owner-thread only, same quiescence gates as `checkpointView`) — new API on an existing runtime file, which must be named in the P16 row's *where* column since the row currently claims the adapter needs nothing it doesn't already have. Either way, add: the restore pass runs on `publishValue` *failure* too (scope-guard it) — a failed promote with unrestored `OpHandle` slots hits the same silent-aliasing hazard r2 diagnosed (`wingOf` falls back to `masterOf(slot)` when `asInt64` fails, `vortex_core.cpp:356-365`).

### 3. MAJOR — `+d.refs` name-records don't link the stale slot they exist to rewrite; two record kinds on one rank, undiscriminated (§6.1 `:873-879`, §6.6 `:1190-1194`, genesis `:1227-1232`)

**Problem.** The task asks whether the name-ref schema conflates two mechanisms on one rank — it does, acceptably, but the schema as written is missing the edge that makes genesis possible. Ref-records carry `+d.values→refcell` + `+d.ref→refcell`; name-records carry `+d.values→label` + `+d.name→qualified name`. Genesis "resolves name-records through `symbol_named`" (`:1230`) — which yields a fresh `CellRef` — but the doc never says *into which cell* `Int64(freshTarget)` gets written. The callee's target slot is a fragment-owned int64 cell (promoted verbatim with stale content, since P16 "does not OpHandle-rewrite name-records" `:1192-1194`); without a `+d.ref→slot` link on the name-record, the re-resolution has no write destination — the promoted `Call` still targets a garbage dense id. Second, the discrimination rule is unstated: the pre-pass "re-kinds every marked ref cell" must *skip* name-record slots — OpHandle-ing a program-side target makes `promote` fail outright (`arena_manifold.cpp:1797-1809`: ephemeral OpHandle target requires `seen.contains(target)`, and program targets aren't `seen`). `+d.name` presence is the natural discriminator; say it. (On the conflation itself: two record kinds on one `+d.step` chain is fine *if* each record's role is structurally distinguishable — the fix makes it so.)

**Fix.** Unify the schema: **every** `+d.refs` record carries `+d.ref→the slot cell genesis must rewrite`; ref-records rehydrate `Int64(*handleTarget)`, name-records add `+d.name→qualified name` (+ the `+d.values→label` provenance field) and rehydrate `Int64(symbol_named(name))`. State the discriminator (`+d.name` present ⇒ name-record ⇒ skip the pre-pass re-kind) in §6.1's layout and §6.6 steps 2/4.

### 4. MAJOR — `learn`'s closedness re-verification names no "state-side" predicate; none is cheap or obvious (§6.6 `:1194-1203`)

**Problem.** `learn` "walks the fragment's `+d.refs` records and capture links checking each endpoint is state-side or a name-record" — the load-bearing predicate of the V12 amendment — but the arena carries no state-vs-program discriminator. `isEphemeral`/`ephemeralBit` (`arena_manifold.hpp:24,462-469`) doesn't map (program cells minted at genesis are ephemeral too); per-cell dimension enumeration is C++-only (`dimensionsOf` — the doc's own U-M7 says no opcode provides it); and the emission-time marker bit (`CompilerBinding` state-side flag, `:1202-1203`) is precisely what the doc calls forgeable by post-emission surgery. A `let`-local capture endpoint isn't on any agent rank either, so naive rank-membership fails for the canonical capture case. As specified, the re-verification cannot be implemented in Vortex — and `learn` *is* Vortex (`std:meta` prelude). An implementer guessing wrong (e.g., trusting the descriptor flag the doc itself calls forgeable) silently reopens the V12 hole.

**Fix.** Name the test and price it. The viable one: a capture endpoint is *unsafe* iff it is reachable from `program()` over the program's own named-dim vocabulary (`d.stdlib`/`d.vars`/`d.clause`/`+d.grab`/`+d.spin`/`+d.step` — all named dims a `Linked`-walk can traverse without enumeration); bounded by the walk's `maxCycles`. Alternatively weaken the claim honestly: re-verification = records-vs-actual consistency (each recorded capture link still names its recorded endpoint, endpoints minted before the fragment) — a weaker, stated property rather than an unnamed strong one. Whichever survives needs a cost line in §7.2.

### 5. MAJOR — the relocation marker's cardinality is unstated; a shared `"cell"` marker is impossible (§6.6 `:1215`, §6.1 `:879-886`, P16 row `:1650`)

**Problem.** Same eviction trap as finding 1, different dim: the doc says each marked ref cell "gets the inert `d.mesh.relocation→"cell"` marker edge" but never says the marker target is **per-ref-cell**. A shared `"cell"`-texted marker reads naturally — it's a constant pair, and §7.2's `d.validate` marker *is* one shared cell per pass — but `link(refB, relocation, POS, marker)` evicts `refA`'s edge via `displacedIt` (`arena_manifold.cpp:1352-1373`), since the marker holds one `-d` neighbour. Then `isCellRelocationHandle(refA)` fails at promote → `promote` returns `nullopt` (`arena_manifold.cpp:1803-1805`) → every checkpoint refuses. The precedent already does the right thing — `arena.makeCell("cell")` *inside* the per-reference loop (`mesh_evaluator.cpp:735`) — but the doc should not rely on the reader inferring it. (Card-carrying note: a per-ref-cell marker is also automatically fragment-owned at emission, keeping the §6.6 reachability invariant clean; a shared program-side marker would technically violate it.)

**Fix.** One clause: "the marker cell is freshly minted per marked ref cell — sharing is impossible, because `link` gives each cell one `-d` neighbour and a second ref's edge would evict the first (the precedent mints per-reference, `mesh_evaluator.cpp:735`)".

### 6. MINOR — `cap$N` resolution inherits `binding()`'s render-check; unvalued capture cells need a stated path (§5.3 `:687-694`, §10.1 `:1620`)

`binding()` does `core_.render(found->second.cell).value()` and refuses non-`contains`/type-mismatched cells (`compiler.cpp:160-181`) — it expects adapter-populated bindings. A `cap$N` alias to a `let`-local or frame-parameter cell points at a cell minted *unvalued* at compile time (`localCells_` are bare `temporary()`s, `:853-855`); `.value()` on an empty render or a missing value crashes/refuses rather than diagnosing. Related ordering gap: a captured let-local's cell exists only after the *enclosing* emission's `:853-855` mint, so the `cap$N`→cell alias can only be materialized if fragment emission is sequenced inside the enclosing `emit` — unstated. **Fix.** One clause: `cap$N` entries bypass the binding-value render check (capture cells may be compile-time-unvalued — the checker already proved the type) — resolved through a `cap$N`-specific lookup into `externalReferences_`, not through `binding()`; and fragment emission runs during the enclosing `emit`, after local cells are minted.

### 7. MINOR — the resolve pass's stamp carrier, recursive invocation, and pipeline driver are unstated (§5.6 `:793-802`, `:815-818`; §10.1 `:1600-1602`)

Three small mechanism gaps in the otherwise-sound single-scope-truth design. (a) The stamp carrier: "stamps each `Identifier` with its binding's scope id" — a `const Expr*`-keyed side table dies under `cloneExpr` (the fragment table keys by `SourceLocation` precisely because pointer-keying fails across clones, `:823-826`); the stamp must be an `Expr` field cloneExpr copies, or re-stamped post-clone. (b) Recursive invocation: `code"…"` bodies are parsed *inside* `expand` (`:811-814`) — their `Identifier`s were never seen by a resolve pass that ran before expansion; `expand` must invoke the shared resolve helper per body subtree seeded with the literal's scope env — which means a scope-id→env table or a scope stamp on the `Code` node itself (also what the checker needs to place `cap$N` env records "at the literal's position", `:688`). (c) The pipeline driver: `check(program, fragments, limits)` is named, but who sequences parse→resolve→expand→check — inside `check()`, a `frontend.cpp` driver, or the artifact builder — is unnamed; it determines whether the frontend test binary's callers see expansion. **Fix.** Three sentences: the carrier (an `Expr` field), the per-body invocation, the driver's name.

### 8. MINOR — captures "referenced by links" requires a wing-slot form `bindInput` never produces; the justification is stale under P16 (§5.3 `:691-693`)

`bindInput`/`bindOutput` **always** wrap operands in `makeScalarCell(int64(operand))` (`vortex_core.cpp:384`, `:402`) — there is no direct-cell wing form in the emitter's vocabulary. The doc's claim that captured cells are referenced "by links (the emission's wing and record edges to the binding cell)" therefore presumes a *new* slot form: link the binding cell as the slot itself, which `wingOf`'s operand lambda already decodes (`asInt64` fails → `masterOf(slot)`, `vortex_core.cpp:356-365` → operand = the cell itself). It works, but only for value-reading ops — `Jump`/`Call` targets read `toInt(inputs[i])` and still need int64 slots — so the emitter needs a distinct capture-slot helper, and `validate`'s wing walk must accept operand-as-cell slots. Also: the justification "an int-encoded capture would re-hit §4.5's staleness hole" is stale — under P16 a marked int64 capture relocates fine; the real reason for links is `closed` verifiability (a linked capture is discoverable by edge, an int needs its record). **Fix.** State the capture-slot form and update the reason clause.

### 9. MINOR — §13's fragment overhead still reads constant-shaped (§13 `:1770-1774`)

"~8–14 cells per `code"…"` literal for head + descriptor + `+d.refs` mark records + `+d.recipe` chain (the recipe is O(fragment cells + links))" — the parenthetical prices the recipe honestly but the `+d.refs` records (~1–2 per op: wing slots + control refs + dim-constant slots) grow with the fragment, so the 8–14 range still reads as total. **Fix.** "O(ops + slots + recipe) per literal; ~8–14 for head+descriptor alone."

### 10. MINOR — `run`'s list literal: materialization still unpriced (§6.2 `:976-982`, §13 `:1775`; r2-12 residual)

`args` is a list literal — lowering a `[Cell]`/`[value]` literal mints a head + O(n) element cells *per `run` call* (`materialize`, `compiler.cpp:733-741`). Either the special form lowers elements straight to frame writes (no list value materialized — say so) or §13 prices the per-call mint. One clause.

### 11. MINOR — the clause-side wrapper memo is single-slot; `test_of`/`body_of` thrash each other (§6.6 `:1159-1166`, M8 `:279-283`)

`clause +d.code → wrapper` is one edge — a clause's *test* memo and *body* memo cannot coexist (the second evicts the first, `arena_manifold.cpp:1369-1373`), so alternating `test_of`/`body_of` re-mints ~6-cell heads every call — correct (miss→re-mint) but the memoization pays off for only one of the two. **Fix.** Say the memo holds one slot per clause (alternating access thrashes) or chain memos `+d.step`.

### 12. MINOR — `run`/`value_of` as checker special forms need the namespace rule §5.1 gives `splice`/`static` (M6 `:225-251`, §6.2 `:995-997`)

`splice`/`static` get an explicit reservation: user `def`/`method`s so named are unreachable as bare calls and the checker rejects them (`:588-591`). `run` and `value_of` are checker special forms bound by name — when `std:meta` is imported, does a user `def run` collide, shadow, or get refused? One clause naming the rule (presumably: builtin member table wins for `!qualifier || "std:meta"`, and a user `def run` is rejected when `std:meta` is imported — matching the builtin-member mechanism at `checker.cpp:765-779`).
