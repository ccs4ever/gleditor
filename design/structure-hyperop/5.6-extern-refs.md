# 5.6 — Persistent references to cells in other stores

Implementation plan for §5.6 of [`structure-hyperop-vision.md`](../structure-hyperop-vision.md).
**Status:** ready to implement, with two corrections. **Unblocks:** §5.7–§5.10, the refiled
[§5.3](5.3-pouch-staging.md), and the bridge's deferred federated link source. **Depends on:** §5.1
for the wire, and shares §5.4's `ValueKind` mechanism.

This is the load-bearing section: every remaining proposal needs a cell in one document to name a
cell in another, and nothing in the tree can do that today.

## 1. R4 already ratified the shape

This is not a new ruling. `store-slice-convergence.md` R4 specifies `GlobalOpRef` and then says:

> `GlobalOpRef` localises through the identical **`Store::externals`/`scrollKey`** path `localise()`
> already models […] **Price.** Two-level indirection on every cross-document cell reference.
> `MicroversionId` is 24 bytes plus a heap allocation, so a `GlobalOpRef` cannot live in a link slot
> — it lives only in packages and in `Manifold::externalCells`.

So the side table, the two-level indirection and the refusal to put a global ref in a node are all
R4's, already priced. What this plan adds is the concrete shape, and two corrections to how §5.6
drew it.

## 2. Correction 1: the local form carries a `ScrollId`, not a scroll key

§5.6 proposed an `externals` section holding `std::vector<GlobalOpRef>` — and a `GlobalOpRef`'s
scroll is a `std::string` global key. That duplicates, once per reference, a name the store already
has in its scroll registry, and it breaks the symmetry the rest of the system is built on:

| addresses… | global / wire form                              | local form                                         |
| ---------- | ----------------------------------------------- | -------------------------------------------------- |
| content    | `GlobalSpan{std::string scroll, start, length}` | `PrimediaSpan{ScrollId scroll, start, length}`     |
| operations | `GlobalOpRef{std::string scroll, produces}`     | **`ExternOpRef{ScrollId scroll, produces}`** — new |

`globalise()`/`localise()` already convert the first row at the publication boundary, and R4's own
sentence says an op ref should localise "through the identical path". So the `externals` table holds
the *local* form, and `opRefOf()`/`localiseOpRef()` handle the string at the wire exactly as spans
do.

Three things fall out, all of them good:

- **No duplicated scroll keys.** A document quoting forty cells from one foreign store holds one
  registry entry, not forty copies of its key.
- **The registry already knows how to fetch it.** `Scroll` carries `segments` — where the bytes are
  — so resolving an extern ref reuses the machinery that resolves a foreign *span*. A cross-store
  cell reference and a cross-store content reference become the same kind of problem.
- **A foreign scroll is registered once, deliberately.** Recording a scroll is already how a store
  says "I address content over there."

## 3. Correction 2: the externals index goes in `value`

§5.6 put the index in the idle `sourceAt`, as §5.4 originally did for handles. The same argument
that moved §5.4 moves this, and the two should agree:

`applyStructure`'s `MakeCell` case already copies `valueKind` and `value` into the slot
(`manifold.cpp:218-226`), so **the fold does not move and `CellSlot` needs no new field**, and the
manifold can answer "what is this a placeholder for" off the slot without a `Store`. `sourceAt` has
no `CellSlot` field and is not on the wire for Structure.

So a placeholder is an ordinary `MakeCell` with `ValueKind::ExternRef = 5` and the `externals` index
in `value` — structurally identical to §5.4's `OpHandle = 4`, which is the point: both say "these
value bits are a reference, and the kind says which table to read it through."

## 4. The design

**Node.** No change. A placeholder is a `MakeCell`; a reference to a foreign cell is an ordinary
`SetLink` whose `to` is that placeholder. The 64-byte node, its alignment and its three
`static_assert`s are untouched, and **no new `StructureVerb` is needed** — the vision floated a
`SetExternLink` verb and it is unnecessary, because the link is local. Only its target stands for
something remote.

**Table.** `store.tables` gains one bencode section beside the existing `scrolls`, `local`, `links`,
`current`, `versions`, `document` keys (`store_tables.cpp:23-28`):

```text
"externals" -> list of { "scroll": ScrollId, "produces": MicroversionId }
```

Entry *i* is the referent of any placeholder whose `value` is *i*. `storeTablesFormatVersion` 3 → 4,
shared with [§5.5](5.5-editions-rank.md)'s bump so the fixtures are regenerated once.

**Fold.** The `MakeCell` case mints the placeholder like any other cell: `spanCount == 0`, no
content, `valueKind == ExternRef`. It is **not** ephemeral — it has an operation behind it — so R8's
refusal and `refusedOps()` keep their meanings exactly. `Manifold` gains `externalCells` (R4's name)
as the set of placeholder refs, and `unresolvedExternals()` as a counter distinct from
`refusedOps()`.

**That distinction is the Nelsonian heart of this section.** A link to a document you do not have
yet is normal in a docuverse; today the fold's only response to an unresolvable target is
`refusedOps_++`, whose documented meaning is "the spool holds something unintelligible." Conflating
"not here yet" with "corrupt" is the error, and §4 of the vision names it.

**Wire.** V4 carries the referent for `ExternRef` placeholders as a `GlobalOpRef` — the scroll as a
global key, the `produces` via `writeMicroversionId` — reusing the same conditional-on-`ValueKind`
mechanism [§5.4](5.4-operation-handles.md) §2 adds for `OpHandle`. One more row in
[§5.1](5.1-compact-binary-v4.md)'s table, not a second bump.

**Merkle cost: zero.** `store.tables` is not in the piece stream, and `ops.nodes` stays a run of
64-byte appends, 1,024 per 64 KiB piece.

## 5. The real cost: resolution is not a lookup

This is where the vision's "resolution on demand, memoised in an arena" hides the actual
engineering, and it should be stated plainly before anyone estimates this section.

To turn a placeholder into a foreign cell you must:

1. find the foreign store — the registry gives you a `Scroll`, i.e. a publisher key, a salt and
   segment locations, **not an open store**;
1. load it, which may mean fetching over BitTorrent;
1. know its `sealedAs` scroll, because `localiseOpRef()` refuses a ref that names another document
   and every history numbers its first state "1";
1. call `localiseOpRef(foreignStore, ref, sealedAs)` for an index — which is `const` and records
   nothing, by explicit design; and
1. **fold a `Manifold` on it**, because an index is not a cell.

So resolving one extern ref costs a document load and a fold. That implies a foreign-store cache
keyed by scroll, with a lifetime policy, which nothing in the tree has — `MultiStoreCoordinator`
composes stores the caller already opened.

**Three states, not two.** `Scroll::segments` "may have gaps: a stretch nobody has sealed yet is
simply not here, and reads as missing rather than as something else." So a placeholder is
*resolved*, *not fetched yet*, or *permanently absent*, and the UI needs to tell the second from the
third — a spinner is not a dead link. `unresolvedExternals()` counts the latter two; distinguishing
them is a resolver concern, not a fold concern.

**The fold never resolves.** `applyStructure` is `noexcept` and allocation-free, and resolution is
I/O. The fold mints placeholders and counts them; a resolver above it fills them in. Keeping that
line sharp is what stops a network fetch appearing inside a manifold rebuild.

## 6. Phasing

The first two phases are self-contained and testable with no network and no second document on disk.

1. **`ValueKind::ExternRef` + the `externals` table + placeholder minting in the fold +
   `externalCells` and `unresolvedExternals()`.** A store can record and reload a reference to a
   foreign cell. It resolves nothing. This is the whole persistent model and it is small.
1. **`Store::makeExternRef(parent, ExternOpRef)`** and the `globalise`/`localise` pair for
   operations (§2), plus the V4 wire row (§4).
1. **The resolver** (§5): a foreign-store cache, the three-state answer, and memoised resolution.
   The largest piece by far, and the one that should be scoped on its own once phases 1–2 exist.
1. **Consumers**: §5.7 anthology ranks, §5.8 quoted ranks, and the refiled
   [§5.3](5.3-pouch-staging.md) pouch model.

## 7. Tests

- **`anExternPlaceholderSurvivesAReload`** — record a reference to a foreign cell, save, load, and
  assert the placeholder is still a cell, still `ExternRef`, and still names the same
  `{scroll, produces}`. The core of phase 1.
- **`anUnresolvableExternIsNotCorruption`** — fold a store whose extern names a scroll the registry
  has no bytes for; assert `refusedOps() == 0` and `unresolvedExternals() == 1`. The distinction
  this section exists to draw, as an assertion.
- **`aRankDeadEndsAtAPlaceholderRatherThanVanishing`** — walk a rank through an unresolved extern
  and assert the placeholder is visited, with empty content.
- **`aPlaceholderIsNotEphemeral`** — `Store::setLink` accepts it where it refuses an `ephemeralBit`
  ref. Guards R8's boundary against being widened by accident.
- **`anExternRefSurvivesTheForeignStoreGainingABranch`** — the R4 regression and the reason none of
  this can be a bare index: seal a foreign store, reference a cell, add a branch to the foreign
  store so its indices renumber, and assert the reference still resolves to the same cell.
- **`anExternRefIsRefusedForTheWrongDocument`** — `localiseOpRef`'s "every history numbers its first
  state 1" guard, exercised through this path.
- **`twoReferencesToOneForeignStoreShareARegistryEntry`** — §2's compaction claim, stated as a test.

## 8. Risk

**Phase 1 is additive and cheap**: no node change, no fold restructuring, one bencode section, one
`ValueKind`. Its only real risk is the one §4 names — if `unresolvedExternals()` is not kept
separate from `refusedOps()`, a normal docuverse condition starts reporting as corruption, and the
counter that is supposed to mean "this spool is broken" stops meaning it.

**Phase 3 is the large and genuinely uncertain one.** A foreign-store cache with a lifetime policy,
fetch-in-progress states, and folds of documents the user did not open is a subsystem, not a
function. It should not be estimated together with phases 1–2, and nothing in §5.7–§5.10 needs it to
*record* references — only to *display* them resolved.
