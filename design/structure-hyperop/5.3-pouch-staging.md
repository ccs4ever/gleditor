# 5.3 — Pouch and clasp staging: the arena is the wrong tool, and the real defect is elsewhere

Review of §5.3 of [`structure-hyperop-vision.md`](../structure-hyperop-vision.md). **Status:
recommend withdrawing the proposal as written and refiling it**, with the replacement sequenced
after §5.6 rather than third in the build order.

This is not an implementation plan, because on reading the code the section turns out to propose
machinery for a problem the tree does not have, while the problem it *does* have sits one layer down
and needs a different fix. §2 is the evidence, §3 the verdict, §4 the real defect, §5 the refiled
proposal.

## 1. What the section claimed

> The bridge's work package 3 builds each pouch item by hand from `contentOf(cell)` spans — a
> hand-rolled arena with none of the mark/release discipline. `ArenaManifold` over a base `Manifold`
> is exactly a staging buffer: the dragged cell shadows its base slot, the base is untouched,
> `release()` is drag-cancel by truncation, and `promote()` on drop is the only write. Buys
> allocation-free drag, free undo, and R8 enforced by the type system rather than by care.

Four claims: work package 3 is outstanding; there is a hand-rolled arena; drag-cancel needs an undo
mechanism; and R8 needs enforcing here. None holds.

## 2. What the code does

**The cell-drop path is built and wired.** `PouchDrawer::handleCellDrop()`
(`apps/xudu/pouch_drawer.cpp:140-182`) exists and is called from the mouse-up handler
(`apps/xudu/main.cpp:2912`), which routes a `PouchOriginKind::ZigzagCell` payload to it and anything
else to `handleGhostDrop()`. It checks the clasp forge's left and right slots, then the drop zones.
Work package 3's "wire Zigzag cell selection and drag into `handleCellDrop()`" is done.

**Drag staging is one payload, not an arena.** The in-flight item lives in
`KineticTetherEngine::payload()`, a single struct, with `cancelDrag()` (`kinetic_tether.hpp:73`) as
the cancel. The drag guide is `ClaspLinkForge::setDragGuide()` (`clasp_link_forge.hpp:84`). There is
no container of staged cells and no multi-select: one drag carries one item.

**Nothing is written during a drag.** The only write is at the drop, in `PouchManager::dropCell()`
(`pouch_zone.cpp:212-261`). So cancelling costs nothing, because nothing had been committed.

**What the drop actually writes** is two things, and neither is a cell:

```cpp
currentVersion_ = store().insertSpan(currentVersion_, 0, span);   // an Insert, not a MakeCell
store().setVersionAnnotation(currentVersion_,
    VersionAnnotation{.alias = zone->id(),      // the zone
                      .description = previewText,
                      .tag = "pouch-cell-drop", // vs "pouch-drop" for a document span
                      .timestamp = ...});
```

**What persists, and what does not.** Zone *definitions* are modelled properly: `system://pouches`
declares them as system-xanadoc cells with schemas and notes (`system_docs.cpp:1120-1145`), read
back by `PouchConfig::fromStore()` (`:2600`). Zone *contents* are not modelled at all —
`DropZone::items_` is a `std::vector<PouchItem>` (`pouch_zone.hpp:137`) that nothing rebuilds on
load. `PouchManager::saveManifest()` serialises only the zone list, as a `|`- and `;`-delimited
string inside a `VersionAnnotation::description` (`pouch_zone.cpp:270-292`), and `loadManifest()`
restores zones, never items.

## 3. Verdict: `ArenaManifold` buys nothing here

Taking the three claimed benefits in turn:

- **"Allocation-free drag."** The drag already allocates exactly one payload. Its cost is the two
  `std::string`s in `PouchItem` (`previewText`, `originRankCoord`), which an arena would not remove
  — an arena holds spans and links, not preview strings. To make the drag allocation-free you would
  stop copying preview text, which is a change to `PouchItem` and has nothing to do with arenas.
- **"Free undo."** Cancelling a drag is already free, because the drag writes nothing.
  `release()`-by-truncation is a solution to committing work speculatively, and nothing here commits
  speculatively.
- **"R8 enforced by the type system rather than by care."** R8 is already satisfied *by
  construction*: dragging is navigation and writes nothing; the drop is the authorial act and is the
  only write. There is no leak for the type system to catch. The section's own closing line —
  "dragging is navigation; the drop is the authorial act; the two-type split says so already" —
  turns out to describe the existing code rather than argue for a change to it.

`promote()` earns its keep when an evaluation builds a *graph* of unknown size and only some of it
should survive — Vlog's solver, VQL's compiler. A drop of one cell emits two or three operations.
Arena-plus-promote for that is more machinery than the direct call it would replace, and the plan
recommends against it.

## 4. The real defect: the pouch has no persistent item model

The section was pointing at something real, one layer below where it looked.

1. **A pouch's contents do not survive a restart.** Items are RAM-only. Meanwhile every drop appends
   an `Insert` and a `VersionAnnotation` to the pouches store forever, and nothing ever reads them
   back — the store grows monotonically to record state the program discards on exit.
1. **The persistence that exists is a record format improvised inside `VersionAnnotation`'s string
   fields**: `alias` carries the zone id, `description` the preview text, `tag` discriminates
   `"pouch-drop"` from `"pouch-cell-drop"`. This is precisely §4's observation — the side tables are
   where authorial acts go when the model has nowhere to put them — and §5.5 already proposes
   retiring `versionAnnotations` entirely. The pouch is its second customer.
1. **A dropped ZigZag cell loses its identity, and could not keep it today even if items
   persisted.** `originCell`, `originSliceIndex` and `originRankCoord` exist only in the in-RAM
   `PouchItem`. And `originCell` is a bare `std::uint32_t` `CellRef` — an operation index into
   *another store's* spool. Per R4, and as [`5.1`](5.1-compact-binary-v4.md) and §5.6 both spell
   out, a bare local index is not a valid cross-store reference: it renumbers when the foreign store
   gains a branch. **The pouch already needs §5.6's persistent extern reference and is currently
   storing an integer that cannot mean anything outside the session that produced it.**

That third point is why this section cannot be built third.

## 5. The refiled proposal: pouch items as cells

The shape, for when §5.6 lands. Not a plan to execute yet — a placeholder with its dependency
stated, so the sequencing is deliberate rather than accidental.

A pouch becomes a slice in `system://pouches` rather than a span chain plus annotations. One cell
per item, on a `d.items` rank off the zone's existing config cell, with:

| what                    | where it goes                                                           |
| ----------------------- | ----------------------------------------------------------------------- |
| the transcluded content | the cell's content span — what it already is, addressed the same way    |
| the preview text        | the cell's content, or a `d.notes` cell; no longer an annotation string |
| the zone                | rank membership, rather than `annotation.alias`                         |
| document vs cell origin | which origin dimension the link uses, rather than `annotation.tag`      |
| a document-span origin  | a link to the operation handle for the originating edit (§5.4)          |
| a ZigZag-cell origin    | a link to the extern placeholder for the foreign cell (§5.6)            |
| the rank coordinate     | derivable from the foreign cell once it is addressable; not a string    |

Three things fall out. Items persist, because they are cells in a store that already loads. The
improvised annotation format disappears, along with the `|`/`;` manifest string. And a dropped
ZigZag cell keeps a reference that still resolves after the slice it came from gains a branch, which
is the whole point of §5.6 and is not achievable any other way.

The clasp forge's two slots (`dropLeft`/`dropRight`, staging a pair to forge a link between) stay as
they are: two `PouchItem`s in RAM, discarded on cancel, written only when the link is forged. Same
argument as §3 — nothing is committed early, so nothing needs an arena.

## 6. Recommendation

**Withdraw §5.3 from position 3 and refile it after §5.6** as "pouch items as cells". The build
order becomes 5.1, 5.2, 5.4, 5.5, 5.6, then this, then 5.7–5.11. Nothing else in the chain depended
on 5.3, so the change costs no other section.

Two smaller things are worth doing regardless, and neither needs a design decision:

- **Stop writing what nobody reads.** Either finish item persistence or stop appending an `Insert`
  and an annotation per drop. Today the pouches store accumulates a record of every item ever
  dropped, which no code path reconstructs, in a format §5.5 is retiring. Of the two, stopping is
  the smaller change and loses nothing that is currently used.
- **Record that `originCell` is not a durable reference.** A one-line comment on
  `PouchItem::originCell` naming R4 and §5.6 costs nothing and stops the next reader assuming a
  `CellRef` in a persisted struct means what it appears to mean. Cheap, and exactly the class of
  stale assumption this whole review keeps turning up.

## 7. What this does not change

`handleCellDrop`, the drag guide, the kinetic tether, the forge slots and the zone hit-testing are
all working and stay as they are. The bridge's work package 3 is further along than
[`xudu-zigzag-hypermedia-bridge-next-stage.md`](../xudu-zigzag-hypermedia-bridge-next-stage.md)
describes; that document should be corrected separately, since its §3 reads as outstanding work.
