# 5.3 — The editions rank: completing a design the code drifted away from

Implementation plan for §5.3 of [`structure-hyperop-vision.md`](../structure-hyperop-vision.md).
**Status:** ready to implement. **Depends on:** §5.2 for the handle a designation points at; §5.1
makes an edition's own history readable. **Provides:** the authoritative `d.editions` model that
§5.4 uses when it removes `currentVersions` and `versionAnnotations` from `store.tables`.

`currentVersions` is an array **on purpose**: the author designates the current French version, the
current English version, and so on, and the UI presents them. Paired with version aliases, that was
the plan for making editions real. The array half has drifted; the alias half is built and on
screen. This section finishes the job by giving an edition an identity of its own.

## 1. The design, and where the code stands against it

| piece                       | intended                                 | today                                                              |
| --------------------------- | ---------------------------------------- | ------------------------------------------------------------------ |
| the set of designated heads | `currentVersions`, one entry per edition | **overwritten from open views on every save** (§2)                 |
| each edition's name         | `versionAnnotation(v).alias`             | **built and rendered** — `hypertime_graph.cpp:281-300`, `:398-504` |
| system stores               | one current version, by concession       | correct — `repointCurrentVersion()`, guarded by `isSystem()`       |
| the UI presenting them      | a list of editions to switch between     | not built; the array never survives long enough to hold two        |

The alias half works. `HypertimeGraph` reads `versionAnnotation()` and draws each alias as a label
beside its node, with collision avoidance (`:189-259`) — real presentation of real authorial names.

**The system-store concession is intact and correct.** Every `repointCurrentVersion()` call in
`session.cpp` (`:117`, `:1053`, `:1702`, `:1821`) is guarded by `st.isSystem()`, and it sets exactly
`{version}` (`store.cpp:1268-1270`). A config document presents one chosen set of values to the
system; that is what the concession says, and the code honours it. `zigzag/main.cpp:117` is the same
path.

## 2. The drift: designations derived from the viewport

`Session::syncCurrentVersions()` (`session.cpp:849-872`) is called unguarded from `Session::save()`
(`:844`) for **every** store, system or not, and replaces the whole array:

```cpp
std::vector<MicroversionId> visible;
for (const auto &view : open) {            // the versions open in windows
  if (view.storeIndex != storeIndex || view.version.isZero()) { continue; }
  if (std::ranges::find(visible, view.version) == visible.end()) {
    visible.push_back(view.version);
  }
}
...
stores[storeIndex].store->setCurrentVersions(std::move(visible));   // clobbers designations
```

This *derives* the author's designations from what happens to be on screen. In the common case the
two coincide — French and English open side by side are the two designated heads — which is exactly
how the drift survived. They stop coinciding the moment anyone scrubs history: open a third state to
compare, hit save, and the document's designations have silently become "the three things that were
on screen."

The drift is now self-documenting, which is worth noticing.
`apps/xudu/batch_orchestrator.cpp:765-774` reasons from it as settled behaviour:

> Those helper views are not a request for a side-by-side presentation: persist one current head for
> each exported store, **while interactive multi-view sessions retain all heads.**

"Interactive multi-view sessions retain all heads" describes the drifted mechanism as though it were
the design. The export path then has to *work around* it by collapsing to one head — a workaround
that would be unnecessary if designations were authored rather than observed.

**Correction to an earlier draft of this plan.** A previous version read the drift as the design and
recommended making `currentVersions` singular, on the evidence that no reader consumes a second
element. That was wrong and would have ratified the drift, destroying the edition model. No reader
consumes a second element because **the array never gets to hold two** — the presentation layer was
never built, and the one writer flattens it to the viewport on every save. Absence of readers was
evidence about what is unfinished, not about what is wanted.

## 3. Why cells, and not just fixing the drift

Fixing §2 alone would restore the embryo but leave its central weakness: **an edition has no
identity.** "The French edition is at microversion X" is stored as two facts in two tables joined by
microversion id — `X ∈ currentVersions`, and `versionAnnotations[X].alias == "French"`.

Repointing French from X to Y therefore means three edits across two containers: drop X from the
array, add Y, and move the alias from key X to key Y. There is no transaction, and worse, **nothing
survives the move**. The alias is keyed by the state it names, so once it moves, the fact that
French was ever at X is gone. An edition cannot be branched, cannot be diffed, and cannot answer
"when did this edition last move, and to what."

As a cell, all of that is free:

| the edition's…   | as a cell                                                                    |
| ---------------- | ---------------------------------------------------------------------------- |
| identity         | the cell itself — it persists across every repointing                        |
| name             | the cell's content, where an alias is today                                  |
| designated head  | a `SetLink` on `d.edition-of` to the [handle](5.02-operation-handles.md)     |
| repointing       | one `SetLink`, one operation, one author, one diff                           |
| its own history  | the cell's R7 chain — [`Manifold::historyOf`](5.01-cell-history.md) reads it |
| per-branch heads | automatic: editions are folded per state, so each future carries its own     |

That last row is what the vision meant by "each branch carries its own heads, which the flat vector
cannot," and it is true — a `std::vector<MicroversionId>` in a side table has no branch dimension.

So §5.3 is a **migration after all**, as the vision said. The correction is only to *what* is being
migrated: not viewport state dressed as authorship, but a real authorial model that two tables are
currently failing to express jointly.

## 4. The shape

Editions live on a `d.editions` rank off `home`:

```text
home ──d.editions──> [ "French" ] ──d.edition-of──> handle(op that produced X)
                     [ "English"] ──d.edition-of──> handle(op that produced Y)
                     [ "1987 text" ] ──d.edition-of──> handle(op that produced Z)
```

- **Minting an edition**: one `MakeCell` (content = the name) plus one `SetLink`.
- **Repointing**: one `SetLink` on `d.edition-of` to a different handle.
- **Listing them**: walk the `d.editions` rank — which is what the unbuilt UI needs, and it is an
  ordinary rank walk rather than a join across two tables.
- **Resolving one**: follow `d.edition-of` to the handle, read its target operation, and that is the
  microversion.

During this step, **`currentVersions` remains only as a transitional cache of the rank**: written
from the fold, never from the viewport, with the rank authoritative when they disagree. The next
step, §5.4, removes the cache once its two-pass bootstrap makes `d.editions` available during open.
Keeping that transition explicit lets the data-loss fix and the new authorial model land before the
larger table migration without pretending the cache is the final design.

`versionAnnotations` moves onto [§5.2](5.02-operation-handles.md) handles. When §5.3 and §5.4 land
in build order there is no standalone table-version bump here: §5.4 deletes that section
immediately.

## 5. Phasing

1. **Stop deriving designations from the viewport** (§2). `syncCurrentVersions()` must not overwrite
   an author's designations on save. Smallest correct change: delete the call from `save()` and let
   designations change only when something designates. Open views then need their own home —
   `system://layout` is the system xanadoc for exactly that — and `batch_orchestrator`'s
   collapse-on-export workaround can go with it. **This is a data-loss fix and is worth landing on
   its own**, before anything else here.
1. **Editions as cells** (§4), needing §5.2 phase 1. Additive: the rank becomes the model while the
   table keeps a cache.
1. **`versionAnnotations` onto handles**, leaving only a transitional reader until §5.4 removes the
   table section.
1. **The UI that presents editions** — a list to switch between, which is what the array was for and
   what has never been buildable while the array held whatever was on screen.

## 6. The `--alias` wrinkle

`apps/xudu/main.cpp:2444` implements `--alias <version>:<name>` by writing a table entry. Under this
section it should mint an **edition cell**, not merely a handle annotation — naming a version is
precisely designating an edition, and that is now an authorial act with a hypertime name. It needs a
writable store and it appears in the history. That is the point, and it is a behavioural change.

## 7. Tests

- **`savingADocumentDoesNotRedesignateItsEditions`** — the §2 data-loss regression, and the sharpest
  statement of the drift: designate two editions, open a third unrelated historical state, save, and
  assert the designations are unchanged. Fails today.
- **`aSystemStoreKeepsExactlyOneCurrentVersion`** — the concession, preserved verbatim.
- **`anEditionSurvivesBeingRepointed`** — mint "French", repoint it, and assert the *cell* is the
  same cell, its name is unchanged, and `Manifold::historyOf()` shows both designations. None of
  this is expressible today, since the alias moves keys and the old designation vanishes.
- **`twoBranchesCarryTheirOwnEditions`** — branch, repoint French on one future only, assert the
  other future still resolves French to the original state.
- **`theEditionsRankAndTheTableCacheAgree`** — after a fold, the cached `currentVersions` equals the
  heads the rank designates; the rank wins if they diverge.
- **`aVersionAnnotationBecomesAHandleCell`** — the §5.2 migration, `--alias` included.

## 8. Risk

**Phase 1 changes behaviour, in the direction of not losing data.** The risk is a workflow that
relies on reopening at the previously-open set of versions; that is worth preserving, but in
`system://layout` where it belongs, not by overwriting the document's designations.

**The §5.4 handoff touches every fixture**, since `store.tables` is present in all seventeen
checked-in sample stores. Regenerate them once after the table migration rather than bumping and
regenerating here only to delete the migrated sections in the next step.

Phases 2 and 4 are additive.

```sh
make -j$(nproc) test TEST_FILTER='*Edition*:*Session*:*StoreTables*:*Sample*'
make -j$(nproc) test && make format-check && make lint
```
