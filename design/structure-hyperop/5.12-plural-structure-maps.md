# 5.12 — Plural structure maps: overlays without a second writer

Implementation plan for §5.12 of [`structure-hyperop-vision.md`](../structure-hyperop-vision.md).
**Status:** ready as a design and last in the build order. **Depends on:**
[§5.2](5.02-operation-handles.md) for named claims, [§5.4](5.04-tables-as-cells.md) for classic-link
cells, [§5.5](5.05-extern-refs.md) for boundary and snapshot descriptors,
[§5.6](5.06-compact-binary-v4.md) for stable publication, [§5.7](5.07-arena-federation.md) for
identity-preserving composition, and [§5.11](5.11-published-vocabularies.md) for cross-store
dimension identity. **Provides:** plural Structure and classic-link layers without adding a second
writer to any target store.

An overlay is another author's sparse structure over cells in one or more documents: an outline, an
argument map, a translator's alignment. It is a separate, signed store. The target stores keep one
writer, and the reader composes their manifolds with the overlay in an arena.

## 1. Build-order position

Federation is infrastructure, not an overlay fold mode, and therefore lands at §5.7. Tables are
already cells by §5.4, so this final step can give Structure claims and classic xanalinks one layer
mechanism rather than promising a later convergence.

The dependency spine is:

```text
5.1 history → 5.2 handles → 5.3 editions → 5.4 tables → 5.5 extern refs
                                                        ↓
5.8 pouch items                              5.6 stable wire → 5.7 federation
                                                                   ├→ 5.9 anthologies
                                                                   └→ 5.10 quotations
                                                                        ↓
                                                                   5.11 vocabularies
                                                                        ↓
                                                                   5.12 overlays
```

§5.7 answers “which cell in which store?” This section answers “whose assertion occupies this
directional slot, and what happened to every assertion that did not?”

## 2. The persistent overlay is a sparse store of named claims

An overlay store contains three kinds of cell:

- **a release root**, whose last operation pins the overlay's own state;
- **boundary placeholders** (§5.5) for foreign cells the overlay touches; and
- **local cells** the overlay contributes, such as outline headings or translator notes.

It uses two ordinary dimensions: `d.overlay-targets`, listing the document snapshots it was authored
against, and `d.overlay-claims`, listing handles to the Structure operations that constitute the
overlay.

```text
overlay root ──d.overlay-targets──> [ Alice/store @ 2a4 ] ──> [ Bob/store @ 7 ]
             └─d.overlay-claims───> [ handle claim 1 ] ─────> [ handle claim 2 ]

[ placeholder: Alice/cell 81 ] ──supports──> [ local cell: "evidence is indirect" ]
                 ^
                 └── claim 1's SetLink subject
```

**A claim is a `SetLink` operation plus a §5.2 operation handle to that exact act.** The handle sits
on `d.overlay-claims`. This is the missing boundary between overlay metadata and the overlay itself:
the store may contain dimensions, notes, release cells and internal links, but only handled
`SetLink`s on the claims rank are composed over another document.

The handle is not ceremony. It preserves three things a final `Manifold` cannot:

- which end was the authored subject;
- an explicit `to == noCell` break, which the final empty slot otherwise erases; and
- the claim's own address, so a reader can comment on or reject one assertion rather than a whole
  package.

No new verb or record is needed. After boundary placeholders have been interned, one positive claim
costs the `SetLink`, one handle `MakeCell`, and one link onto `d.overlay-claims`. A break costs the
same. The release root is touched last, as §5.11's vocabulary release is, so its final operation
pins the complete overlay state.

## 3. A document state is not a cell reference

The vision says an overlay records which sealed state of the base it was written against. A
`GlobalOpRef` is not quite that type: it names one operation and only incidentally names the state
that operation produced. Requiring the base's home cell to be edited last would make publication
order an addressing rule.

Use §5.5's distinct `GlobalDocumentState` semantic type. It is persisted as ordinary descriptor
content, not as a new operation-wire record. Each cell on `d.overlay-targets` carries the canonical
versioned, length-prefixed encoding of `scroll` followed by `writeMicroversionId(version)`, and is
also filed beneath the corresponding scroll cell through `d.scroll-refs`. The overlay may name more
than one target, because a translator's alignment is inherently over two documents.

Every foreign subject or target named by a claim must:

1. belong to one of the declared target scrolls; and
1. name an operation ancestral to that target's version.

A reference outside the snapshot is an invalid overlay claim, not corruption in the target store. It
is reported separately from `Manifold::refusedOps()`, whose meaning remains “this spool could not be
understood.”

## 4. Composition produces an effective view and keeps every candidate

The persistent stores are never merged. The reader builds a fresh arena over §5.7's federated tissue
and a side index of claims:

```cpp
enum class OverlayClaimState : std::uint8_t {
  Applied,
  Shadowed,
  SlotConflict,
  TargetNotFetched,
  TargetAbsent,
  OutsideSnapshot,
  Unintelligible,
};

struct OverlayCandidate {
  zigzag::CellRef claimHandle{zigzag::noCell};
  zigzag::CellRef from{zigzag::noCell};
  zigzag::DimRef dimension{zigzag::noCell};
  zigzag::DimVector direction{zigzag::POS};
  zigzag::CellRef to{zigzag::noCell};
  ProminenceTier tier{ProminenceTier::Public};
  std::int64_t score{0};
  OverlayClaimState state{OverlayClaimState::Unintelligible};
};

struct OverlayAttachment {
  const xanadu::Store *store{nullptr};
  const xanadu::Scroll *sealedAs{nullptr};
  PublicKey publisher;
  std::string publicationKey;
  std::int64_t sequence{0};
};

class OverlayComposition {
public:
  [[nodiscard]] const zigzag::ArenaManifold &view() const noexcept;
  [[nodiscard]] std::span<const OverlayCandidate>
  candidates(zigzag::CellRef from, zigzag::DimRef dim,
             zigzag::DimVector direction) const noexcept;
};
```

`view()` exposes the one effective link per `(cell, dimension, direction)` that existing `walkRank`
and every current consumer require. `candidates()` preserves the plural structure map: who asserted
each alternative, its tier, and why it did or did not appear in the effective view. Discarding the
losers would reproduce the side-table defect in memory — the answer would be visible and its
provenance gone.

The side index is derived, arena-owned and rebuilt with the composition. It earns no operations
under R8.

## 5. Precedence is a two-slot arbitration, not last-writer-wins

A ZigZag link occupies two directional slots: `(from, dim, dir)` and `(to, dim, opposite(dir))`.
Applying claims one at a time with `ArenaManifold::link()` would let a later reciprocal write
silently evict an earlier winner. Selection therefore happens before any link is materialised.

1. Mark every intrinsic link in each target manifold as occupying both slots. The target author's
   own structure is the highest-prominence candidate and is never erased by a third-party overlay.
1. Sort overlay claims by tier, discovery score, publication identity, then claim microversion. The
   last two are stable tie-breakers, not additional trust signals.
1. A positive claim is accepted only when both of its slots are free. Otherwise it remains visible
   as `Shadowed` or `SlotConflict`.
1. An explicit break (`to == noCell`) occupies its subject slot and suppresses lower-ranked overlay
   claims for that slot. It cannot suppress an intrinsic target link or a higher-ranked claim.
1. Materialise accepted positive claims with `ArenaManifold::link()`, which supplies the reciprocal
   edge. Materialise no break; the occupied-slot set already expresses its result.

This is a deterministic greedy matching, not “last store attached wins.” Attachment order may vary
with network arrival and must have no semantic effect.

**Base structure always wins in the default policy.** An overlay most often adds a new dimension,
where there is no conflict. A reader who wants Carol's alternative `d.outline` instead of Alice's
can select Carol's layer as a view policy, but that does not rewrite either store and is not the
default meaning of `ProminenceTier::Author`.

## 6. Prominence belongs to the reader's trust graph

`ProminenceTier` already means:

- `Author`: bundled with or signed by the target document's author;
- `Curated`: selected through the reader's subscribed curator graph; and
- `Public`: discovered from the bounded public rendezvous.

An overlay author cannot write “Author” into their own store and become the target's author. The
tier is assigned when the reader attaches the overlay, using the verified publisher, target
publication and the existing blessing/follow graph. For a multi-target overlay the tier is computed
**per target**, because Carol may be the author of one side of an alignment and a third party to the
other.

The ranking arithmetic in `LinkDiscoveryEngine::rankPackages()` already implements followed
curators, author blessings, transcluded-author blessings and bounded public results. Extract that
policy over a small signed-package descriptor and reuse it; do not fork an almost-identical overlay
ranking engine.

The overlay's signed publication supplies authorship and immutability. The reader supplies
prominence. Keeping those separate is what makes the same publication public to one reader and
curated to another without either reader changing the author's history.

## 7. Composition, step by step

Given a target state and ranked overlay publications:

1. **Fetch and fold each declared target at its exact `GlobalDocumentState`.** Shape needs the full
   operation path and small reference descriptors, but no target document content, as §5.10
   establishes.
1. **Attach the target manifolds to §5.7's arena.** Their cells receive lazy identity-preserving
   proxies; nothing is copied.
1. **Fetch and fold each overlay at its release.** Attach it as another space so its local outline
   cells also keep their identities.
1. **Walk `d.overlay-claims`.** Resolve each handle, require that it names a `Structure/SetLink`,
   follow its `sourceOpIndex` chain to the subject's `MakeCell`, and read dimension, direction and
   target from the named operation rather than reconstructing them from the final manifold.
1. **Translate references.** A boundary placeholder becomes the target-space proxy; a local overlay
   cell becomes its overlay-space proxy; a published dimension resolves through §5.11's shared
   identity bound set. A private overlay dimension remains scoped to that layer and is not equated
   with a same-spelled target dimension.
1. **Validate snapshot ancestry** (§3), assign prominence (§6), and collect candidates.
1. **Arbitrate both slots** (§5), then write only accepted claims into the arena.
1. **Expose diagnostics and provenance** beside the effective view. No resolver state is persisted
   and no target or overlay store is mutated.

Cycles are ordinary: an overlay can cite a second overlay or a target can quote the overlay author's
work. Attachment is cycle-bounded by `(scroll, version)`, the same guard §5.10 uses for quotations.

## 8. Pinning, staleness and rebasing

An overlay pins every target state. Applying it silently to “whatever Alice currently publishes”
would let another author's edit change Carol's map without an operation in Carol's history, the
moving-reference failure §5.9 already rules out.

When a reader is viewing a later target state, the overlay is **stale but still valid against its
pinned state**. The UI may show it beside the later state or offer a rebase. It must not quietly
reinterpret the claims against the later manifold merely because every `GlobalOpRef` still
localises.

Rebasing is an authorial operation in the overlay store:

1. resolve every old claim against the new target state;
1. report missing, off-branch and semantically conflicting slots;
1. append a new target descriptor and replace its link on `d.overlay-targets`; and
1. touch the release root last, producing a new pinned overlay release.

The old release remains addressable. “What outline did Carol publish for Alice@2a4?” therefore has
an answer after Alice and Carol have both moved on.

## 9. Publication and discovery

An overlay is an ordinary `Publication` carrying V4 Structure operations. Its signature is the
author identity; its release microversion is the immutable state. No second overlay package format
is needed.

Discovery adds one rendezvous namespace keyed by each target scroll, parallel to
`linkPackageRendezvousTarget()`:

```text
sha1("structure-overlays:" + targetScrollKey)
```

The advertised item identifies the overlay publication and its release; after fetching it, the
reader verifies the signature and checks that the target descriptor actually names the rendezvous
document. A multi-target alignment is advertised under every target key but fetched once by
publication identity.

Public discovery stays bounded by the same policy as link packages. An unbounded set of third-party
structure maps is both a denial-of-service surface and an unreadable interface.

Because [§5.4](5.04-tables-as-cells.md) has already made a classic butterfly link a cell, the same
overlay publication may carry both Structure claims and xanalink cells, and the same prominence and
discovery path can rank them. Core Structure claims land first within this step. Classic butterfly
links then reuse publication, identity, provenance, discovery and trust ranking, **not** the
two-slot ZigZag edge arbitration: multiple links may share an endpoint span, and forcing them
through one-neighbor slots would erase legitimate plural links. Keep a multivalued link index and
test overlapping endpoint spans rather than creating another layer format.

## 10. Phasing

1. **Overlay vocabulary.** Define `d.overlay-targets` and `d.overlay-claims`, and document the
   release-root convention over the already-landed §5.5 snapshot descriptor.
1. **Persistent overlay authoring.** Helpers to declare targets, append a handled claim, append an
   explicit break, and seal a release. No composition yet; test by reloading the store.
1. **Single-overlay composition** against in-memory target stores: reference translation, snapshot
   validation and the two-slot arbitration, all at `Author` tier.
1. **Plural composition and prominence:** candidate index, deterministic tie-breaks, curated/public
   tiers and explicit layer selection.
1. **Publication and discovery** (§9), reusing generalized link-package ranking.
1. **Rebase tooling and UI:** stale state, claim diagnostics, layer/provenance inspection, and an
   authored rebase.
1. **Classic xanalinks join the same layer**, after the Structure path establishes arbitration,
   without changing that path.

## 11. Tests

- **`anOverlayWritesOnlyItsOwnStore`** — author a claim and assert the target's op count, latest
  microversion and manifold are unchanged. The one-writer rule as an assertion.
- **`anOverlayClaimIsAHandledSetLink`** — reload an overlay and recover subject, dimension,
  direction and target from the operation named on `d.overlay-claims`.
- **`anExplicitBreakSurvivesTheFold`** — a handled `SetLink(..., noCell)` remains a break candidate
  even though the final overlay manifold slot is empty. The reason claims use handles.
- **`aClaimOutsideThePinnedSnapshotIsRejectedSeparately`** — reference an operation added after the
  declared target state; assert the claim is `OutsideSnapshot` and target `refusedOps()` remains 0.
- **`anOverlayMayAlignTwoTargetStores`** — one handled claim links proxies from two declared target
  states and materialises a reciprocal edge without copying either cell.
- **`intrinsicStructureOutranksEveryOverlay`** — author, curated and public claims all contest an
  occupied target slot; the base link remains effective and all three alternatives remain
  inspectable.
- **`aHigherTierBreakSuppressesOnlyLowerOverlayClaims`** — the break wins over lower-tier overlays
  but cannot erase an intrinsic base link.
- **`reciprocalSlotConflictsAreResolvedBeforeMaterialisation`** — two claims whose opposite ends
  collide produce one symmetric effective edge and one `SlotConflict`, never an asymmetric rank.
- **`networkArrivalOrderDoesNotChangeTheView`** — attach the same publications in every order and
  assert identical effective links and candidate states.
- **`anOverlayAuthorCannotSelfAssignAuthorProminence`** — a public overlay whose cells claim an
  author tier remains public; the verified target publisher is the authority.
- **`aPrivateDimensionDoesNotBindBySpelling`** — an overlay-local `supports` stays distinct from a
  target-local `supports`; citing the same §5.11 term binds them.
- **`anOverlayPinsAndRebasesAsTwoReleases`** — compose against the old state, rebase onto a later
  state, and assert both releases remain reproducible through hypertime.
- **`anUnavailableOverlayIsNotTargetCorruption`** — missing overlay bytes produce
  `TargetNotFetched`/`TargetAbsent` diagnostics and leave the base view intact.
- **`publicOverlayDiscoveryIsBounded`** — more candidates than the configured public limit return
  the deterministic top set, reusing the link-discovery ranking policy.
- **`pluralButterflyLinksShareAnEndpoint`** — two links with the same durable span end both remain
  discoverable; two-slot arbitration applies only to ZigZag directional `SetLink` claims.

## 12. Risk

**Precedence bugs are silent structural corruption of the view.** Applying claims in fetch order or
resolving only the subject slot can produce a plausible but asymmetric rank. The normalized two-slot
arbitration and the arrival-order test are the central safeguards.

**The operation-handle index is deliberate overhead.** It adds two operations around every claim,
but without it an explicit break disappears in the fold and overlay metadata links are
indistinguishable from claims. Sparse overlays touch dozens of cells, not every cell in the target;
the addressability and auditability are worth the constant factor, and should still be measured on a
large argument map.

**Discovery is an attack surface.** A signed overlay may be valid and enormous. Apply both a
publication-size budget and a claim-count budget before folding, then retain §5.10's cell/depth
budget during attachment. “Valid signature” is not “safe amount of work.”

**Staleness must remain visible.** Automatically applying a pinned overlay to a newer target because
its references happen to resolve turns a reproducible map into a moving one. The rebase path exists
so the resolver never needs that shortcut.

```sh
make -j$(nproc) test TEST_FILTER='*Overlay*:*Federat*:*Extern*:*Handle*:*Discovery*'
make -j$(nproc) test && make format-check && make lint
```
