# 5.2 — Operation handle cells: giving an edit an address

Implementation plan for §5.2 of [`structure-hyperop-vision.md`](../structure-hyperop-vision.md).
**Status:** ready to implement, with one correction to the encoding. **Depends on:** §5.1 only for
the history assertion; the mechanism itself is independent. **Provides:** `ValueKind::OpHandle` and
the handle API consumed by §5.3, §5.4 and §5.12. Publication is completed by §5.6 after every
address-bearing `Structure` field has a stable wire shape.

An `Insert`, a `Delete`, a `Transclude`, the making of a link: each is a permanent, named act of
authorship, and none of them can be pointed at. A handle cell is the address.

## 1. The correction: the target goes in `value`, not `sourceAt`

The vision proposed carrying the referenced operation index in the node's idle `sourceAt`, marked by
a spare `ValueKind`. The marker is right and the field is wrong, and the vision's own justification
for the marker is what shows it:

> the marker is a spare `ValueKind`, `ValueKind::OpHandle = 4`, not flags bit 7. It is a statement
> about what the cell's value *is*, which is what `ValueKind` is for.

A `ValueKind` that describes a field other than `value` is not that statement. Putting the target in
`value` instead is better on four independent counts, and costs nothing:

- **The fold needs no change at all.** `applyStructure`'s `MakeCell` case already copies both halves
  into the slot — `.valueKind = valueKindOf(node.flags)` and `.valueBits = node.value`
  (`manifold.cpp:218-226`). `sourceAt` has no `CellSlot` field and would need one.
- **The manifold can answer without a `Store`.** `handleTarget()` becomes a three-line accessor
  beside `asInt64()`, reading `valueBits` off the slot. With the target in `sourceAt` the manifold
  would have to re-read the op node, which means a `Store` and the same read-path compromise
  [`5.2`](5.1-cell-history.md) §2 had to argue for.
- **`value` is already on the wire.** The `BinStructure` record writes it (`binary_ops.cpp:265`);
  `sourceAt` is not written for Structure at all, so that route needs a brand-new field.
- **It is exactly the scalar precedent.** R6 already uses `ValueKind` to say how to read `value` —
  `Double`, `Bool`, `Int64`. `OpHandle` is the same sentence with a fourth noun.

The existing accessors then do the right thing for free: `asDouble`/`asBool`/`asInt64` all test the
kind and return `nullopt` on a mismatch (`manifold.cpp`, e.g. `asDouble`), so a handle cell is never
silently read as a number.

`ValueKind` is a three-bit field with `None=0, Double=1, Bool=2, Int64=3` (`ops.hpp:140-145`), so
`OpHandle = 4` is free with three spare after it. Only three files switch on the enum — `ops.cpp`
(`valueKindName`, which already falls through to `"unknown"` and whose comment says a build reading
a newer spool is exactly when that matters), `enfilade/arrayfilade.cpp` and
`vql/ascii_visualizer.cpp`. Each needs a case; none is a wide change.

## 2. The requirement handed to §5.6

**A handle cannot be published correctly as a raw `value`, and the failure would be silent.**

`value` travels as a plain varint. An operation index is only meaningful in the spool that produced
it — it renumbers when the publisher adds a branch, which is the whole of R4 and the reason
[`5.1`](5.6-compact-binary-v4.md) §3 writes `source` as a `MicroversionId`. A published handle would
therefore arrive pointing at *a different operation*: not a load failure, a change of meaning. That
is the R14 failure the `Splice` refusal already exists to prevent, arriving by a second door.

So V4's `BinStructure` record gains one more conditional, keyed the same way the others are:

```text
V4  tag [produces] flags to link span.scroll span.start span.length value
                                                                    source
                                                                    [at length]        iff verb == Splice
                                                                    [target-as-name]   iff valueKind == OpHandle
```

When the kind is `OpHandle`, write the target with `writeMicroversionId(out, idOf(target))` and let
the reader re-localise through `indexOf()` — the same mechanism, the same guarantee. The raw `value`
varint is then redundant for that kind and should be written as zero.

**Land this in §5.6's single V4 bump.** This section deliberately precedes the wire plan so the
encoder is specified only after every address-bearing value kind is known. Catching it after V4
ships would cost a V5.

## 3. The API

```cpp
// Store. Deliberately not an overload of makeCell(), for the same reason
// makeScalarCell() is not: an implicit conversion capturing the wrong overload
// is a silent mistake, and a handle is a different kind of thing.
MicroversionId makeOpHandle(const MicroversionId &parent, std::uint32_t target,
                            std::string_view text = {});

// Manifold, beside asInt64(). Nothing when the cell is not a handle.
[[nodiscard]] std::optional<CellRef> handleTarget(CellRef ref) const noexcept;
```

`makeOpHandle` mints an ordinary `MakeCell` with
`structureFlags(MakeCell, false, ValueKind::OpHandle)` and `value = target`, spooling `text` as the
cell's content span exactly as `makeCell(text)` does. `sourceOpIndex` keeps its R7 meaning
untouched: the handle's own chain begins and ends at its own `MakeCell`, and the referenced
operation is data, not a chain link. (The draft's first version routed the handle through
`sourceOpIndex` to the referenced operation, which would make `denseOf()` resolve a text operation
to a cell — a category error the fold cannot detect. Withdrawn already; recorded here so it is not
reinvented.)

**Validation happens at mint, not in the fold**, matching how R6 handles a signalling NaN:
`scalar.cpp` refuses one when the cell is minted, and `applyStructure` stores bits without
inspecting them. So `makeOpHandle` checks that `target` names a real operation and refuses an
`ephemeralBit` reference (R8, the same refusal `setLink` already makes), while the fold keeps
copying `value` blind and stays `noexcept`.

One consequence worth stating: **a handle may point at any operation of any kind** — that is the
point. The existing `Store::requireCellOp()` is the wrong check here; it demands a Structure
operation, and a handle to an `Insert` is the primary use.

## 4. What it buys, in order of how soon it pays

- **Commentary on an edit.** "Why was this deleted." Nothing in the tree can express it: the `Link`
  table addresses spans, and an operation is not a span.
- **Version annotations, retired from the side table.** `VersionAnnotation` is four strings —
  `alias`, `description`, `tag`, `timestamp` (`store_tables.hpp:89-96`) — in a
  `std::map<MicroversionId, VersionAnnotation>`. As a handle cell: the alias and description become
  content, the tag becomes rank membership or a `d.tag` link, and the timestamp is already implicit
  in the operation. Five production call sites (`apps/xudu/main.cpp:2444`, `pouch_zone.cpp` ×3,
  `system_docs.cpp:1601`), which is the whole migration surface. This is where §5.3 starts.
- **Links-to-links without touching Non-Goal 4.** Making a link is itself an `OpKind::Link`
  operation. A handle to *that act* is commentable and linkable while the `Link` record keeps its
  spans and its table. This is why the draft's separate "link handle cell" idea collapsed into this
  one with nothing lost.
- **A review rank of edits** — ordinary cells on an ordinary dimension, once edits have addresses.

## 5. Refused, and why

- **A slot per operation.** A `CellSlot` plus its `byRef` entry for every operation is roughly +75%
  resident over the nodes, to serve a table nobody queries. Handles are minted **on demand** — one
  cell where a comment exists.
- **A handle naming a `linkId`.** That is a durable name for a mutable table row, which inherits the
  disease rather than curing it. The handle names the operation.
- **Decomposing `Link` records into cells merely to make the act addressable.** A handle solves that
  narrower problem without multiplying the link representation. §5.4 later moves links for the
  different reason that cross-author link sets need hypertime identity; it pays and benchmarks that
  wider cost explicitly.

## 6. Phasing

1. **`ValueKind::OpHandle` + `makeOpHandle()` + `handleTarget()`**, plus the three `valueKindName`-
   style switch arms. The fold is untouched. Fully usable in-store.
1. **The V4 conditional** (§2), landing in [§5.6](5.6-compact-binary-v4.md) after this in-store API.
1. **Version annotations onto handles** — the first real application, and the opening move of §5.3.

Phases 1 and 2 are independent of each other in code and can land in either order; only publication
needs both.

## 7. Tests

In `tests/xudu/manifold_test.cpp` and `tests/xudu/binary_ops.cpp`.

- **`anOpHandleNamesTheOperationItWasMintedFor`** — mint a handle over an `Insert`; assert
  `handleTarget()` returns that index and `valueKindOf()` is `OpHandle`.
- **`anOpHandleIsNotAScalar`** — `asDouble`, `asBool` and `asInt64` all answer `nullopt` on it. The
  guard against a handle's index being read as a number.
- **`aHandleHasItsOwnHistory`** — its `sourceOpIndex` chain terminates at itself, and
  `walkCellHistory()` ([`5.2`](5.1-cell-history.md)) over it returns one entry. R7 unbroken.
- **`aHandleMayNameAnyKindOfOperation`** — `Insert`, `Delete`, `Link`, and another `MakeCell`.
- **`anEphemeralTargetIsRefused`** — `makeOpHandle` throws on a ref carrying `ephemeralBit`, as
  `setLink` does.
- **`aPublishedHandleStillNamesTheSameOperation`** — the §2 regression: publish a store containing a
  handle, add a branch to the publisher *after* sealing so indices renumber, ingest, and assert the
  handle resolves to the same operation. Without the V4 conditional this test fails silently today,
  which is the point of writing it.

## 8. Risk

**Additive, and the fold does not move** — the single biggest reason to prefer `value` over
`sourceAt`. No existing signature changes; no stored layout changes; `CompactOpNode` keeps its size,
alignment and `offsetof(value) == 56`.

The one real risk is §2's silent wrong answer, and it only exists on the publication path. An
in-store handle cannot be wrong about its target, because no renumbering has happened. The
mitigation is to land the V4 conditional with 5.1 and to write
`aPublishedHandleStillNamesTheSameOperation` before the encoder, not after.

A second, smaller one: `ValueKind` gains an enumerator, so any `switch` without a `default` becomes
a warning under the tree's `-Werror` settings. Three files, all named in §1 — and that warning is
the desirable behaviour, since each of them genuinely needs to decide what to print for a handle.

```sh
make -j$(nproc) test TEST_FILTER='*Handle*:*BinaryOps*:*Manifold*'
make -j$(nproc) test && make format-check && make lint
```
