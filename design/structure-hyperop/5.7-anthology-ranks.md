# 5.7 — Cross-store ranks: the anthology

Implementation plan for §5.7 of [`structure-hyperop-vision.md`](../structure-hyperop-vision.md).
**Status:** ready, and **thin by design** — it is mostly an application of
[§5.6](5.6-extern-refs.md). **Depends on:** §5.6 phases 1–2 to *record* an anthology, phase 3 to
*display* one.

A syllabus, a compilation, an issue of a journal: a rank whose members live in other people's
documents. One placeholder `MakeCell` and one `SetLink` per member, and the mechanism is already
specified. What this plan adds is the two decisions §5.7 does not make, and a closed question.

## 1. What is genuinely new here

Almost nothing in the machinery, which is the point — §5.6 was built to carry this. An anthology is:

```text
home ──d.anthology──> [ placeholder → Alice's ch.3 ] ──> [ local note ] ──> [ placeholder → Bob's §2 ]
```

Members may be local cells or placeholders, mixed freely on one rank. `walkRank`
(`manifold.hpp:119-160`) already traverses it without modification, because a placeholder is an
ordinary local cell — that is exactly why §5.6 chose a placeholder over a tagged `to` field.

The three things worth deciding are in §2, §3 and §4.

## 2. The distinction from `d.stores` is sharper than the vision states

`MultiStoreCoordinator` (`vql/multi_store.hpp`) already has a `d.stores` rank off home, and the
vision notes 5.7 is "distinct from" it. The distinction is worth stating exactly, because it is the
Nelsonian argument in miniature:

|                         | `d.stores` (built)                                                                                | `d.anthology` (this section)                       |
| ----------------------- | ------------------------------------------------------------------------------------------------- | -------------------------------------------------- |
| a cell represents       | a whole store                                                                                     | one cell inside another store                      |
| how the content arrives | `importManifold()` **copies** every cell, dimension, link, span and scalar into a composite arena | a reference; nothing is copied                     |
| lifetime                | ephemeral — the arena dies with the query                                                         | persistent operations in the anthology's own store |
| purpose                 | "load these documents into one workspace to query across them"                                    | "this compilation cites these passages"            |

`importManifold` *reproduces*. An anthology *quotes*. That is the whole of Nelson's anthology
argument, and the tree currently has only the reproducing half.

Neither replaces the other. A VQL query over five documents still wants the composite arena; a
published syllabus wants references.

## 3. Ruling: an anthology pins a state; it does not track a moving one

§5.6's `ExternOpRef{ScrollId, produces}` names **a specific microversion** of the member's document.
So an anthology entry pins: "Alice's chapter 3, as it stood at this state." The alternative — track
whatever Alice's current French edition happens to be, by naming the foreign store plus an
[edition](5.5-editions-rank.md) name and resolving at read time — is a *different kind of reference*
and §5.6 does not provide it.

**It should not.** Tracking would make a document's content change because somebody else edited
theirs, and that breaks the property the whole model rests on: a document is what its own edit
decision list says it is. An anthology that silently re-points is no longer an object its compiler
can stand behind — you could not cite it, diff it, or know what a reader saw.

The price, stated honestly: **an anthology goes stale, and refreshing it is an authorial act.**
"Update to Alice's second edition" is a `SetLink` to a new placeholder, with an author, a date and a
diff. That is the correct cost, and it is the same answer transclusion already gives for content.

This does leave a real convenience unserved — "a syllabus that always assigns the current text" —
and if that is wanted later it is a **new reference mode with its own ruling**, not a tweak to this
one. Recorded here so it is not smuggled in as an implementation detail.

## 4. Closed: U1 does not bite at anthology scale

A rank answers successor and predecessor, not "the *n*-th thing" (U1), so "item 7 of the syllabus"
is a walk. For an anthology this is fine and the question can be closed rather than deferred:
anthologies are tens of members, not thousands, and every access pattern they have — render the
list, step to the next item, jump to a member the user clicked — is either a full walk of a short
rank or a bounded walk from a cursor. That is precisely the condition U1's experiment names for the
concession holding.

U1 remains open for what it was actually about: a scrollbar over a five-thousand-cell `d.2`. An
anthology is not that. (Note in passing that U1's experiment text points at `assets/zigzag/`, which
no longer exists — the YAML slice format was deleted. The experiment needs a new corpus before it
can be run.)

## 5. Display: three states per member, on a rank

The one place this needs code beyond §5.6 is rendering, and it inherits §5.6 §5's three-state
problem per member: **resolved**, **not fetched yet**, **permanently absent**. On a rank they appear
together — a syllabus where two members are cached, one is downloading and one is from a store that
has gone dark.

So an anthology view renders a *heterogeneous* list, and must not collapse the middle state into the
last. A member still fetching is a spinner; a member whose scroll has no bytes and no seeders is a
broken citation, and the difference is the difference between "wait" and "this compilation has
rotted."

Nothing here needs new fold machinery: `unresolvedExternals()` gives the count, and the resolver
(§5.6 phase 3) gives the per-member state.

## 6. Phasing

1. **`d.anthology` as a convention, not code.** Given §5.6 phases 1–2, an anthology is already
   expressible: mint placeholders, link them on a rank. What is needed is a dimension name, a
   `Store` helper (`appendToAnthology(parent, rank, ExternOpRef)` — one `makeExternRef` plus one
   `setLink`), and tests. Small.
1. **Rendering** (§5), once §5.6 phase 3's resolver exists.
1. **Refresh as an authorial act** (§3) — a `SetLink` to a new placeholder, and UI for "this member
   has a newer state upstream", which needs the resolver to notice.

## 7. Tests

- **`anAnthologyMixesLocalAndForeignMembersOnOneRank`** — walk a rank of three, middle one local,
  and assert `walkRank` visits all three in order with no special-casing.
- **`anAnthologyMemberPinsItsState`** — the §3 ruling as an assertion: reference a foreign cell,
  advance the foreign store past that state, and assert the anthology still names the pinned one.
- **`anAnthologySurvivesAMemberGoingDark`** — a member whose scroll has no bytes: the rank still
  walks, the placeholder is still visited, `refusedOps() == 0`, `unresolvedExternals() == 1`.
- **`refreshingAMemberIsAnOperation`** — repoint a member and assert the anthology cell's R7 chain
  ([§5.2](5.2-cell-history.md)) shows both states, so "what did this syllabus assign last term" is
  answerable.

## 8. Risk

**Low, and almost entirely inherited.** No new node fields, no new verb, no format change beyond
§5.6's, no fold change. The rank walk is unmodified.

The one risk specific to this section is §3 being quietly violated later — a well-meaning "keep the
anthology up to date" feature that re-points members automatically would turn a citable compilation
into a moving target, and would do it without any operation recording that it happened. The ruling
is in §3 precisely so that change has to argue for itself.

```sh
make -j$(nproc) test TEST_FILTER='*Anthology*:*Extern*:*Manifold*'
make -j$(nproc) test && make format-check && make lint
```
